### 测试抓到的真 bug（值得记）
`BytesSink::write_chunk` 原本用**硬编码 `CHUNK_SIZE`** 算偏移 `seq * CHUNK_SIZE`，
但块大小应该来自 meta。**块大小不一致时会静默把文件写坏**。
→ 改成 `BytesSink` 携带 `chunk_size` 字段；并补了三个针对性测试：
- `sink_verifies_hash`（整除）
- `sink_handles_partial_last_chunk`（末块不足 / 非整除块大小 —— 10GB 文件必然遇到）
- `sink_detects_wrong_chunk_offset`（故意用错块大小，**校验必须失败**）

### 本轮修掉的 4 个真 bug（都很值得记）

1. **事件订阅是"竞争"而不是"广播"**（架构级缺陷）
   `RoomNode::subscribe()` 原本返回 `events_rx.clone()`。`async_channel` 的多个 receiver 是
   **竞争**关系（一条消息只给其中一个），所以两个订阅者会互相抢事件：
   实测表现为"后台日志任务抢走了邀约，业务逻辑永远收不到"。
   → 改成**扇出**：内部单一消费者读原始通道，再复制给订阅者列表；订阅者关闭时自动剔除。
   **这个 bug 在浏览器端同样会犯**（UI 和传输逻辑各订一份就完了）。

2. **`my_relay_url()` 读缓存快照有竞态**
   原本读 `latest_status`（watcher 异步刷新的快照），握手刚完成时可能还是空 → 返回 `None`
   → 对方拿不到我的中继地址，**拨号无门**。实测两次运行结果不一致（一次 Some 一次 None）。
   → 改成直接问 endpoint：`home_relay_status().get()` 遍历取已连接的那台。
   ⚠️ 注意它返回的是 **`Vec<RelayStatus>`** 而不是单个。

3. **`Accept` 消息不带"谁接受的"**
   发送方原本靠"遍历 peers 找一个不是自己的"，房间人多时会猜错。
   → `FileAccepted` 事件加 `by` 字段（从 `SignedCtrl.from` 取）。

4. **FileService 的 ack 方向错了**（设计缺陷）
   原本服务层自己去读流的 ack —— 但**只有上层知道文件是否真的写盘成功、哈希对不对**。
   → 改成双通道：`expect()` 返回 `(块接收端, 回执发送端)`；服务层等上层回执（600s 超时）再转达发送方。

## 【浏览器侧文件传输 API 完成】10:55

### 设计（关键决定：读写交给 JS，传输留 Rust）
10GB 不可能进 WASM 内存，所以：
- **Rust 只负责**"要第 N 块"（`JsChunkSource`）和"写第 N 块"（`JsChunkSink`）
- **真正的 I/O 由浏览器 API 做**：读用 `File.slice()`，写用 `showSaveFilePicker()` 的 `createWritable()`
- 块数据经 `Uint8Array` 过界，每次只有一块（16KB），**内存恒定**

### wasm 新增导出（`src/wasm_api.rs`）
| 类/方法 | 作用 |
|---|---|
| `JsChunkSource(read)` | JS 传 `(seq, size) => Uint8Array`，Rust 按需拉块 |
| `JsChunkSink(write, finish, abort, rootHash, size, chunkSize)` | Rust 推块给 JS 写盘 |
| `JsHasher()` | **增量**哈希（10GB 不能一次性算） |
| `RoomNode.file_meta(name,size,mime,rootHash)` | 生成含根哈希的元信息 |
| `RoomNode.invite_file(metaJson)` | 广播邀约 |
| `RoomNode.accept_and_receive(fileId, metaJson, haveB64, write, finish, abort)` | 接受并接收 |
| `RoomNode.send_file_to(metaJson, peerId, peerRelay, haveB64, read)` | 拨号发送 |
| `RoomNode.reject_file(fileId, reason)` | 拒绝 |

### 关键坑：`LocalBoxFuture` 的 `Send` 约束
`js_sys::Function` / `JsValue` **不是 `Send`**，而原生（cli）需要 `Send`。
→ 用 `#[cfg(target_arch = "wasm32")]` 给出两种定义：
wasm 版不带 `Send`（浏览器单线程，本来也不需要）。**一个类型别名不能同时满足两端。**

## 【重大 bug 修复：wasm 没有 std::time / process::id】11:35

### 现象
用户点"发文件"报 `发起失败：Failed to fetch dynamically imported module: js/pkg/iroh_web.js`
→ 修好路径后又报 `unreachable`（wasm 里 Rust panic 的兜底提示，**没有任何有用信息**）

### 定位方法（值得复用）
wasm 的 panic 在 JS 里只显示 `unreachable`，必须**挂 console.error 去抓**：
```js
const o = console.error.bind(console);
console.error = (...a) => { window.__errs.push(a.map(x=>String(x?.message ?? x)).join(' ')); o(...a); };
```
然后就能看到真正的 panic：
```
panicked at .../sys/time/unsupported.rs:35:9: time not implemented on this platform
panicked at .../sys/process/unsupported.rs:336:5: no pids on this platform
```

### 三个真 bug（同一个根因：**wasm32-unknown-unknown 缺平台实现**）
1. **`now_ms()` 用了 `std::time::SystemTime::now()`** → wasm 下 panic。
   **影响面很大**：聊天消息的 `ts` 也走它 → **浏览器里发消息一直在 panic**（被静默吞掉）。
   → 分平台：wasm 用 `js_sys::Date::now()`
2. **`new_file_id()` 用了 `std::process::id()`** → wasm 下 panic（我刚引入的）
   → 改成 `now_ms() + 自增 AtomicU64 + 内存地址`（零平台依赖）
3. **`HistoryStore` 的 `std::fs::*` 没有 cfg 保护**
   虽然有 `if let Some(dir)` 运行时判断（浏览器传 None 所以不会执行），
   但那是"靠调用方守规矩"，很脆弱 → 加 `#[cfg(not(target_arch = "wasm32"))]`
   + wasm 下给空的 `load_from_disk()` 保持调用点不变

### 教训（已写进 skill）
**写跨平台（原生 + wasm）代码时，任何"取时间 / 取进程号 / 访问文件系统 / 读线程"的调用都要先想：这个平台上存在吗？**
`std::time`、`std::process`、`std::fs`、`std::thread` 在 `wasm32-unknown-unknown` 上**全部没有实现**，
调了就是 panic —— 而且 panic 信息在 JS 里只显示成 `unreachable`，**极难定位**。
**建议**：这类调用一律走一层薄封装（如 `now_ms()`），在封装里做 cfg 分平台，
这样只需要在一个地方正确，而不是满项目找。

### 另一个坑
`js/pkg/...` vs `pkg/...`：`js/ui/xxx.js` 里引用根目录的 `pkg/` 要用 `../../pkg/`（两层），
我写成了 `../pkg/`（一层）→ 404。**改完 import 后务必校验路径存在**
（我用脚本扫所有 `from '...'` 并对文件系统做存在性检查）。
