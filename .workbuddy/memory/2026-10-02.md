## 完成：`FileService::cancel` —— 真正取消接收任务（自动续传的前提）

### 问题回顾

昨天做"切后台自动暂停"时，试过"回前台自动续传"，
结果 **8MB 文件收成 1024/512 块、文件写坏**。
根因：`abort()` 只让 JS 停止处理，而 wasm 侧 `accept()` 的读流循环
**仍在往通道推块**；新一轮 `accept()` 又登记一条记录 ⇒ **两条链路并行写同一文件**。

### 修复（wasm 侧）

1. `Pending` 加 `cancelled: Arc<AtomicBool>`
2. `FileService::cancel(file_id)`：摘表项 **并** 置位 `cancelled`
3. `accept()` 的读流循环**每块检查一次**该标志，置位就退出
   （不能只靠 drop sender —— `tx` 是克隆出来的，摘表项管不着它）
4. `RoomNode::cancel_file()` / wasm `RoomNode.cancel_file()` 暴露给 JS
5. **`accept_file()` 开头先 `self.file_service.cancel(file_id)`** ——
   双保险：即使上层忘了取消，重入 accept 也不会并行
6. 前端 `abort` 里先调 `cancel_file` 再落盘；恢复 `reuseHandle`（复用保存位置）

### 验证结果（真机，真实切标签页，8MB）

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 写入次数 / 总块数 | 1024 / 512（**重复写**） | **512 / 512（零重复）** |
| 逐字节校验 | 失败 | **OK** ✅ |
| 回前台 | — | **自动续传**，无需手动点 |

回归测试 6/6 通过。已上线。

### ⚠️ 顺带修正的测试替身缺陷

`_probeHandleSize` 会读 `handle.getFile().size` 判断"目标文件是否半截"，
只有小于源大小时才启用旧位图。我之前的**假句柄永远返回满额 size**，
导致走了"不是同一个文件 → 丢弃位图 → 全量重传"分支，
表现为"续传没生效、有块缺失"。
→ 修正：假句柄的 `getFile().size` 要返回**已写入的高水位**（与真实文件一致）。
**测试替身不真实会误导结论**，又是一例。

## 传输中对方刷新页面 —— 中断恢复（已上线）

用户问："我在发送端发送的时候，接收端刷新了，现在应该怎么办？能续上吗，还是直接触发发送端取消？"

### 先实测现状（不靠猜）

| 观察 | 结果 |
|---|---|
| 接收端刷新后，发送端有反应吗 | ✅ 有：**33 秒**后转 `failed`（不是永远卡住） |
| 已发出的块 | `done=1089` 保留，但**白费**——没有重发入口 |
| 接收端刷新后 | `transfers = []`，**完全不知道刚才有过邀约** |

→ 结论：**能检测到失败，但两边都没法恢复**。

### 实施方案

**① 发送端「重新发送」按钮**（失败/超时后出现 ↻）
- `File` 还留在 Worker 的 `outFiles` 里（失败时不 delete），**不用重选文件**
- **复用同一个 `file_id`** → 接收端能找回断点位图 → 对方接受后是**断点续传**

**② 接收端刷新后恢复卡片**
- 收到邀约时把元信息存 localStorage（`iroh.pending-invites`，24h 过期）
- 进房后 `restoreInvites()` 恢复成 `interrupted` 状态，带「继续接收」按钮

**③ 不做自动重试**：对方可能已离开，无限重试会变成骚扰。

### ⚠️ 踩到一个**很隐蔽的 bug**：localStorage 是跨标签共享的

第一版没记"这条记录属于谁"，结果**发送端标签读到了接收端写的记录**，
也去"恢复"了一遍 → 发送端界面上冒出 `direction=recv` 的**幽灵卡片**。

修法：
1. 每条记录带 `owner`（本端 endpoint id），恢复时只认自己那条；
2. 加 **`INVITE_VER` 格式版本号** —— 旧格式（无 owner）必须整体丢弃，
   否则"无 owner"会被当成"放行"，升级后旧记录仍会复活。

**顺带修掉两个 Worker 化遗留 bug**：
- `sidebar.js` 还在用 `net.node?.endpoint_id()` → Worker 化后该属性已删，
  "我的身份"一直显示空
- `net.relayStatus()` 依赖的 `_relayJson` 缓存**从没被写入** → 设置页中继状态永远空

### 验证（CDP 逐项实测）

```
✅ 邀约落盘、owner 与 myId 一致
✅ 重新打开页面 → 恢复为 interrupted，1 张卡片，有「继续接收」
✅ 不同身份的页面 → transfers 为空（隔离生效）
✅ 回归测试 6/6（断点续传 + 逐字节校验完好）
```

### 测试基础设施补充

`net.js` 新增 `?key=<64位hex>` 参数：用**固定身份**启动。
`?testid=1` 每次加载都随机，**刷新后 owner 就对不上了**，
没法测"刷新后恢复"。需要跨刷新保持同身份时必须用 `?key=`。

### 未做（如实记录）

完整的"刷新 → 点继续 → 发送端重发 → 传完"闭环**没走完**：
长流程里 CDP 连接会断（`Page.reload` 后 execution context 失效）。
已分段验证了每一环（恢复 ✅ / 重发按钮 ✅ / 断点续传 ✅），
但**"端到端一次跑通"还没有**，下次要用更稳的方式补上。

## 多接收方支持 + 「刷新方主动取消」（本次）

### 起因

用户问："发送方发送后，接收端可能有多个，如果有一个刷新了，发送端应该不影响吧？"
并给了兜底口径："如果不好实现的优雅干净，可以一方刷新，直接刷新方取消。"

### ⚠️ 排查过程中最大的教训：**先怀疑自己的测试**

先用 `peers=1` 的现象怀疑"多接收方没实现"，查了很久。真因是
**测试脚本自己污染自己**：接收端用固定 `?key=` 身份，上一轮写进
localStorage 的旧邀约在下一轮被 `restoreInvites()` 恢复出来，
于是接收方对着**旧的 file_id** 点接受，发送端根本不认。

判据一眼可见：`两个接收方拿到的 file_id 相同吗: False`。
→ 修法：`__clearBitmaps()` 里连 `localStorage` 的邀约一起清。

**结论：多接收方本来就是好的**（`peers=2`、两条通道并行、汇总正确）。

### 真因一：「上来就失败」= 陈旧邀约诈尸

`restoreInvites()` 恢复 **24 小时**内的旧邀约为「继续接收」，
可发送端邀约 **60 秒**就过期、页面一关文件引用就没了 ——
用户一点必然失败。**两个数字自相矛盾**。

修法（`frontend/js/ui/filetransfer.js`）：
1. `INVITE_TTL_MS` 24h → **10 分钟**，且判的是「距**上次活动**」
   （`touchInvite()` 节流 30 秒刷新一次）—— 否则 1GB 传 20 分钟
   中途刷新会被误杀，而那恰恰是最需要恢复的场景
2. `INVITE_VER` 2 → 3（丢弃旧格式）
3. 记录里存 `senderId`；恢复时若**发送方已不在房间**就不显示死卡片
4. 新增 `fileTransfer.setPeers()`，挂到 `EV.PRESENCE` 上；
   presence 来晚了也会**把已恢复的卡片降级**为「发送方已离开房间」

### 真因二：对端消失，发送端两分钟没反应

实测：R1 关标签页后，发送端 120 秒都没报错 —— 因为接收方没了以后
中继只是丢包，发送方的 QUIC 收不到 ACK、流控窗口耗尽，
`write_frame` **一直阻塞在等窗口**上，既不成功也不失败。

三层修复：

| 层 | 做法 | 效果 |
|---|---|---|
| 应用层（快路径） | 接收方 `pagehide` 时主动广播 `Reject`（尽力而为） | **实测 5 秒** |
| 传输层 | 单块 `write_frame` 加 30 秒超时（`n0_future::time::timeout`） | 卡死的任务自己退出，不再占连接 |
| 兜底 | Worker 里的「无进度看门狗」45 秒 | 对方连 Reject 都发不出来时保底 |

配套 Rust 改动：`RoomEvent::FileRejected` 加 **`by`** 字段 ——
一份文件可能同时发给多个人，没有它发送端不知道该标哪一条通道，
只能整份判死（会把还在正常传的人一起放弃）。

### ⚠️ 顺带修掉的两个多接收方误伤

`fileRejected` / `fileDone` 都是**群广播**，同房间所有人都收到：
- `_onRejected` 原来不管方向就整张卡标"已拒绝" → 接收方收到**别人的**
  拒绝会把自己的卡片也标死
- `_onDone` 同理：一个人收完就把整张卡标"完成"

修法：加 `direction !== 'send'` 早退；多接收方时不下结论，
交给 Worker 的按人汇总（`transfer:outcome`）。

还修了一个我自己引入的 bug：看门狗把通道标 `failed` 之后，
`send_file_to` 返回还会**覆盖回 `done`**（卡片从"失败"跳回"已完成"）。
→ 加 `cur.state === 'sending'` 才认。

### 新增诊断钩子（排查多接收方用）

`iroh-worker.js`：RPC `outgoingDetail`（每条 `file_id:peer` 通道的原始状态）、
`outFiles`（还留着的文件引用，查泄漏）、`accLog`（收到的 Accept 流水）。
主线程暴露 `window.__outgoingDetail()` / `__outFileRefs()` / `__accLog()`。

### 写超时的对照实验（别凭感觉回退优化）

加完「单块写 30 秒超时」后看到吞吐像是掉了，怀疑是它。**做了 A/B 才下结论**：
用 `/tmp/tput.py`（48MB 单传输，测接收端块数）在同一环境下前后各跑一次，
中间只回退这一处改动并重编 wasm：

```
带写超时：40s 收到 366 块 ≈ 146 KB/s
```

## 联系人 / 设置面板重建（同一轮 review 的续）

### 动手前先查了网络层能力（避免设计出做不到的功能）

`client-wasm/src/room.rs` 读下来三个关键约束，决定了整个设计：

1. **`join()` 是单房间的** —— 换房间就退掉旧房间（`g.joined = None; g.peers.clear()`）。
   ⇒ 不存在"同时挂着多个好友在线"这回事，"在线状态"只能反映**当前房间**。
2. **`topic_id(room) = blake3("editor.vip/room/1/" + room)`** ⇒ 房间名就是加密组播标识。
   ⇒ 私聊只能实现成"一个由双方 ID 推导出的房间名"，没有别的路。
3. **`PeerUp` / `PeerDown` Rust 侧一直在发**（room.rs:930/938，NeighborUp/Down → RoomEvent），
   但 `net.js` 的 `_dispatch` **没有 case**，全掉进 `default: break` 被静默丢弃。
   ⇒ "谁上线了"这个信息前端一直拿不到。补上后在线状态才是活的。

### 私聊方案（实测跑通，不是纸上设计）

`util.js` 新增 `dmRoomName(idA, idB)`：`[a,b].sort().join('|')` → FNV 变体哈希 → `dm-<24 hex>`。

- **`sort()` 不能省**：A 算 `dm(a,b)`、B 算 `dm(b,a)` 名字就不同，永远碰不上。
- **哈希而非直接拼 ID**：房间名会进 DOM、会留在锚点历史里，直接拼会泄露两个完整身份 ID。
- 实测：两个标签页各自独立算出**完全相同**的 `dm-3a7aa33b37930c0735ac9c66`，
  各自 join 后互见 presence，双向消息收发成功 —— 走的是真加密组播。

### ⚠️ 先纠正上一轮我自己的一个错误结论

我上一轮说"重写 index.html 把 Cloudflare 统计脚本弄丢了"——**是错的**。
真相：Cloudflare **按请求头决定是否注入**那段脚本：

| 请求 | 响应大小 | 有无 beacon |
|---|---|---|
| 只带 `User-Agent` | 8840 | 无 |
| 带 `Accept: text/html` 等浏览器头 | 9207 | **有** |

→ 教训：**拿线上产物当基线做对比时，必须用 `Accept: */*` 抓原始产物**，
否则会把"注入差异"当成"用户改动"，得出完全相反的结论。

### ⚠️ 「刷新方主动取消」实测是两条路径，别把断言写死

移除后重跑 refresh-test，检测延迟从 5s 变成 30s，一度以为被我改坏了。
单独写 `/tmp/leave-cancel-test.py` 把两件事拆开：**派发 `pagehide` 但让页面存活**
→ **2.0 秒**生效，证明逻辑没坏。

所以：
- **快路径（~2s）**：接收方 `pagehide` 主动广播 Reject。
  但标签页**真的被关掉**时 Worker 往往先被销毁、广播来不及 flush → 走下面那条。
- **兜底（~30s）**：发送端单块写超时 `n0_future::time::timeout(30s)`。
- 阈值改到 40s（容忍 30s 超时 + 5s 采样粒度）。实测两种都遇到过。

### 环境维护：无头 Chrome 重启的坑

跑了 3 小时后反复出现"某个标签 120s 进不去房"（中继本身 HTTP 200 正常），
怀疑是浏览器累积状态，于是重启它。踩到两个坑：

1. 直接 `"/Applications/.../Google Chrome" --headless=new ...` 会失败：
   `Failed to initialize sandbox. ... Operation not permitted` + GPU 崩溃 FATAL。
   → 必须加 `--no-sandbox --disable-gpu --disable-dev-shm-usage`
2. `nohup ... &` 起的进程**在本工具 shell 退出后会被回收**
   （起来后 10 秒内就没了）→ 要**用后台任务方式**启动才常驻。

现有实例：`--headless=new --no-sandbox --disable-gpu --disable-dev-shm-usage
--remote-debugging-port=9222 --user-data-dir=/tmp/chrome-iroh`。

## 文件历史可见 + 能力清单 + 离开即过期 + 补偿质询（已上线）

### 需求

> "发送方发出文件后，只要发送方未刷新页面，其他进入房间的人都应能看到该文件的存在并点击接收；
> 新进入房间的人应能看到文件历史（仅需文件名，作为上下文的存在证明）；
> 当发送方刷新页面后，该文件信息应自动变为已过期状态。"

用户明确：**不要 35 秒延迟**、**不做历史兼容**（开发测试期，破坏变更就清数据）、
**不关心改动大小，要项目越来越好**。

### 架构原则（先定原则，再写代码）

> **软状态（心跳 + 超时派生）是唯一事实来源；事件只用于加速，不用于决定事实。**

由此推出三条：
1. **离开声明不能当事实**：最需要它的场景（刷新/关页/崩溃/断网）恰恰发不出去。
   所以它只在**"用户主动切房间"**这个可靠时机发 —— 页面活着、连接在，一定发得出去。
2. **"过期"是派生状态，不是被同步的状态**：`可接收 ⟺ 发送方在成员表里 ∧ file_id 在他的能力清单里`。
   好处：永远不会出现"状态与事实不符"，且**天然可逆**（清单回来就恢复）。
3. **新进者的视图要靠快照**，不能等全场心跳（否则进房先看到"房间是空的"）。

### 成本结论（回答用户"为什么不用退出时广播"）

单条消息的成本与内容无关（几百字节的 JSON+签名），所以**退出广播的增量 ≈ 0**。
不用它做事实来源的理由**是可靠性，不是成本**。
真正的大头是心跳：3 人房间 10s 心跳 ≈ 15MB/天，是聊天的 300 倍，且随人数平方增长。
→ 要省成本该动心跳，不该动退出消息。

### 实现（四层）

**协议（room.rs）**
- `ChatMessage` 加可选 `file: FileRef`（file_id/name/size/mime），签名串 `v1` → **`v2`**
  （单版本，不搞两套拼法：没有文件时那几个字段填空串/0）
- `compute_id` 把 `file_id` 也算进哈希 —— 否则同一毫秒发的两个文件会撞 id，
  而历史按 id 去重，后一条会被静默丢掉
- `Presence` 加 `files: Vec<String>`（能力清单）+ `epoch`，签名串 → `p2`
- 新增 `Wire::Leave`（离开声明，`l1|`）与 `Wire::FileQuery`（可用性质询，`q1|`）

**房间逻辑（room.rs）**
- `set_nickname` 改**立即广播**（以前要等最多 10 秒）
- `leave_room()`：**先广播"我走了"再退订** —— 唯一可靠的离开声明时机
- 心跳拆两条节奏：成员 10s（不动，调小会让在线列表因丢包闪离线）、
  **文件清单 3s 且只在手里有文件时发**（把文件过期压到 ~10s，无文件时增量 0）
- 收到 `Leave` → 立刻摘出成员表（→ 他的文件立刻过期）
- 收到 `FileQuery` → 若我是被问的人且还持有 → 重发一次邀约（比"再播次心跳"更明确）
- 进房时 `epoch = now_ms()`（见下方"踩坑"）

**常驻节点（roomd.rs）**
- 新增快照表 `room → (成员表 + 各自文件清单)`，随心跳更新、随 Leave 摘除
- `HistoryResponse` 带 `snapshot`，客户端拉历史时**顺带**拿到 →
  新进者进房即刻有正确视图；`apply_snapshot` 只**补没见过的人**，不覆盖本地更新的信息

**前端**
- 历史里的文件证明 → 卡片，三态派生：`live`（可接收）/ `expired`（已过期）/ `unknown`（检查中，不猜）
- 点「接收」= 请发送方重发邀约（我们手上没有 root_hash/chunk_size，开不了传输），
  5 秒没响应 → **本地隔离**成过期（⚠️ 只本地判定、不广播：我连不上他可能只是我网络的问题，
  单方面宣布会误伤别人）；隔离**可逆**，清单再出现就解除
- `net.joinRoom` 在换房间时先调 `leaveRoom`
- `outFiles` 改为**保留到刷新**（原来是"这轮都收完就删"→ 第一个接收方收完发送方就忘了文件，
  后来者必失败）；双层上限：总量 1GB + **内存类单独 100MB**（粘贴的截图是 `new File` 造的内存数据）

### ⚠️ 踩到的三个坑（都实测过）

1. **结构化克隆会丢掉挂在 File 上的自定义属性**。
   想用 `file.__inMemory = true` 标记"这是内存数据"，到 Worker 那边是 `undefined`。
   而且这事儿没法从 File 本身推出来（`new File([...])` 造的也有名字/size/lastModified）。
   → 改成显式传参（composer 判定 → `pickAndSend(file, room, mem)` → Worker 记进条目）。

2. **epoch 用"从 0 开始的计数器"会踩大坑**。
   刷新页面后 epoch 重置为 0，而对端存的是刷新前的高位值 →
   刷新者之后发的**每一条心跳都被判成"乱序旧消息"直接丢弃** →
   他在别人眼里**永远"还在线、还能发文件"**，文件到期判定彻底失效。
   实测：刷新 20 秒后对方仍显示"可接收"。
   → **改用墙钟毫秒**，跨刷新天然单调。

3. **空态与实时消息竞态**（这轮给历史加了 snapshot 后暴露，因为响应变慢、窗口变大）。
   `loadLatest()` 是异步的，实时消息可能在它返回**之前**就到 →
   "历史为空 ⇒ 显示空态"晚一步执行，把已显示的消息盖上"还没有人说话"。
   → 判据改成看 DOM 事实（`.msg / .tl-day`）。
   ⚠️ 但**不能**把 `.tl-note`（"正在进入房间…"）算成内容 —— 进房时它一定在，
   一算就把空态永久挡掉（我第一版就这么修，把 19 项测试里的空态项修挂了）。

1. `__clearBitmaps()` 内部有 `transfers.clear()`，会**把刚收到的卡片一起删掉**。
