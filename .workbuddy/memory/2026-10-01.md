### 挖出并修掉的 4 个真 bug（1 个是数据静默损坏级）

1. **`STOP_AFTER_CHUNKS` 只声明没接线** —— 钩子在 `filetransfer.rs:51` 定义了，
   但 `send_file` 的发送循环从没读它，所以"发了全部 64 块"。已接到发送循环。
2. **构建脚本漏同步源文件**（**这轮最费时的根因**）——
   `scripts/build-wasm.sh` 是逐个 `scp` 指定文件的，**没带 `filetransfer.rs` /
   `transfer_orchestrator.rs` / `room.rs`**，构建机上常年跑旧代码。
   表现就是"源码改了、编译过了、行为不变"。
   → 改成 `rsync -az --delete src/`，一劳永逸。
3. **接收方从不校验"是否收齐"**（**数据静默损坏级**）——
   `receive_file` 收到 `End` 就直接 `sink.finish()`，而 `JsChunkSink.finish()` 只调
   JS 的 close 回调、不做任何校验。对端中途停下也会正常 EOF →
   **把半个文件当成功交付，不报错、还删了位图**。
   → `JsChunkSink` 自己维护已收位图，`finish()` 时 `missing_chunks()` 非空即 `bail`。
4. **续传轮的位图没带"已有块"作为初始状态** ——
   只统计本轮收到的块 → 第 2 轮补完 32 块后仍被判"缺 32 块" → 状态错误地停在 `failed`。
   → 构造函数接收 `have_b64` 并预置进去。

## 追加：发送端状态机修复（用户报"接收端已完成、发送端还在传输中"）✅

### 根因（第 5 个真 bug，隐蔽度最高）

`transfer_orchestrator.rs::send_file` 等接收方回执时用的是 **`tokio::time::timeout`**，
而 wasm32-unknown-unknown 上**没有 tokio 运行时**——这个计时器既不触发超时、
也永远不返回，于是发送端 Promise 永不 resolve，卡片永远停在「传输中」。
（同一文件里接收侧 `filetransfer.rs` 一直用的是 `n0_future::time::timeout`，
所以只有发送端中招——**同一功能两条路径用了两套 timer，只错了一边**。）

**教训**：wasm 项目里排查"某处永久挂起"，先全局搜 `tokio::time`。
本项目此前也踩过 `std::time` panics（见 skill），`tokio::time` 是它的同类变体。
修复：统一改用 `n0_future::time::timeout`。

### 发送端状态机重新设计（这是设计问题的正解）

原来的问题不只是 bug，语义也没分清：接收端"已完成"= 数据落盘+校验通过；
发送端"已完成"= **收到对方回执**。二者天然存在时间差，UI 必须把它们分开表达。

```
发送端:  pending(等待对方确认) → active(传输中, 带进度) → sent(已发送，等待对方确认) → done
                                                              ↑ 新增的中间态
接收端:  invited(等待你确认) → active(接收中) → done(已完成)
```

- 新增 `sent` 态，文案「已发送，等待对方确认」——覆盖"本地已发完、对方还在校验"的空窗。
- 新增 `expired` 态（邀约 60s 无人响应 → 「对方未响应」），
  修掉"对方不点就永远停在等待对方确认"的问题。
- `send_file_to` 增加 `on_event` JS 回调，把进度和 `sent` 阶段回传前端——
  此前**发送端进度条根本不动**（Rust 侧 `SendEvent::Progress` 被闭包吞掉、没透出到 JS）。
- 进度按**整文件**折算（`base = t.total - e.total`），续传时不会显示成"从 0 开始补几块"。

### 验证
`scripts/transfer-test.py` 扩到 **6 项断言全绿**，含：
`发送端最终进入终态（不再卡在「传输中」）`、`发送端最终状态为 done`。

### 修改文件
- `client-wasm/src/transfer_orchestrator.rs`：tokio→n0_future 超时；加"已发完/收到回执"日志
- `client-wasm/src/wasm_api.rs`：`send_file_to` 新增 `on_event` 进度回调
- `frontend/js/ui/filetransfer.js`：`sent`/`expired` 态、邀约超时、整文件进度折算

## 排查：文件传输只有 100 多 KB/s（用户报"慢得离谱"）

### 结论（先给答案）

**瓶颈是「浏览器 ↔ 中继」这一段广域网传输，不是服务器带宽、不是写盘、不是协议设计。**
中继本身极快：在中继本机跑两个原生客户端，**32MB 仅 223ms（≈128 MB/s）**。

实测数据：

| 路径 | 吞吐 |
|---|---|
| 中继本机原生端到端（不出机） | **128 MB/s** |
| Chrome → Cloudflare（im.editor.vip） | 1~2 MB/s |
| 本机 → 香港（SSH，纯 TCP） | ~600 KB/s |
| **浏览器 iroh → 香港中继** | **~50 KB/s** ← 问题在这 |

### 逐项排除（每条都有实测支撑）

1. **不是服务器**：8 核负载 0.4~0.7，中继容器 CPU 2.7%。
2. **不是中继限速**：中继配置无 `[limits]`；源码里 `None => Default::default()` = 不限速。
3. **不是写盘**：把 sink 换成纯内存假句柄，吞吐一样（78 KB/s）。用 OPFS 真句柄也不变。
4. **不是每块开销**：**把块从 16KB 放大到 256KB，吞吐纹丝不动**（78 → 48 KB/s）。
   这条最关键——它一次排除了"往返次数/唤醒次数"这类假设。
5. **不是我们的读路径**：给发送循环加了耗时分解，**读源 259ms / 写网络 100043ms**
   （读只占 0.26%，99.7% 卡在 `write_all`）。

### 机制判断

浏览器里的 iroh **只能用 WebSocket（TCP）连中继** —— iroh 1.3 全仓库没有
WebTransport 支持（`grep -r webtransport` 为空），浏览器端实现是 `ws_stream_wasm`。
于是 QUIC 报文被塞进 TCP 隧道：**TCP 和 QUIC 两层各自拥塞控制互相踩**，
在高 RTT（到香港 80ms）链路上会严重塌缩。同一路径上纯 TCP（SSH）有 600KB/s，
而 QUIC-over-TCP 只有 50KB/s，**12 倍差距**，符合这个已知病态。

另外：两个浏览器标签在同一台机器时，数据要**出境到香港再入境**，跨境两次。

### 已排除的错误方向（别再试）

- 调块大小 ❌（已验证无效）
- 加并发流 ❌（同理，不是往返次数问题）
- 换中继线路 ✅ **这个才是有效方向**（中继物理位置 = 浏览器方案的性能上限）

- `scripts/transfer-bench.py`：吞吐基准，支持 `mem`/`opfs` 两种 sink 对照 +
  块到达间隔统计 + 标签置前（验证后台节流假设）

### ⭐ 决定性实验：换一个近的中继，问题就消失了

用户提出一个很准的质疑："**我的服务器跑 FTP/MinIO，浏览器上传都快得很，凭什么 iroh 慢？**"
为了回答它，我把环境整个换掉重测了一遍。

**做法**：本机装 `iroh-relay`（`cargo install iroh-relay --features server`）+ 本机跑
`roomd` 当锚点，把前端指向 `http://127.0.0.1:3340`（relay 的 `--dev` 模式），
RTT 从 80ms 降到 ~0.1ms。**其余全部不变**（同一份浏览器代码、同一份协议、同一个中继程序）。

| 配置 | 吞吐 | 写网络耗时 | 块间间隔 |
|---|---|---|---|
| 浏览器 + **本地**中继 | **16 MB/s** | **1ms** | **0.7ms** |
| 浏览器 + 香港中继 | 50 KB/s | 100043ms | 155ms |

**320 倍差距，全部来自中继的物理距离。**

另外测到的对照数据：
- 用户浏览器**上行 ≈ 1 MB/s**（POST 到 `speed.cloudflare.com/__up`：4MB→558KB/s，8MB→1034KB/s）
- 本机原生 ↔ 原生（自动走直连，不经中继）：**67 MB/s**
- 中继本机原生：**128 MB/s**

### 最终结论（回答"为什么 FTP/MinIO 快，iroh 慢"）

| | FTP / MinIO | iroh 浏览器版 |
|---|---|---|
| 连接 | 浏览器 → 服务器**直连** | **不能直连**（浏览器发不了 UDP，打不了洞） |
| 跳数 | 1 跳 | 2 跳（本机→中继→对方） |
| 传输层 | 纯 TCP | QUIC **套在 WebSocket(TCP) 里**（iroh 1.3 无 WebTransport，已全仓库确认）|

**协议无罪、服务器无罪、浏览器实现无罪 —— 唯一的变量是中继离用户有多远。**
`scripts/iroh-wasm-client` skill 里已记下这个方法。

### 追加：用户追问"延迟凭什么影响速度" —— BDP 才是准确答案

用户质疑得对："距离只代表延迟，跟速度有什么关系？"

**准确的机制是带宽时延积（BDP）**：`吞吐上限 = 在途数据量 ÷ RTT`。
用实测反推在途量：

| 场景 | RTT | 吞吐 | 反推在途量 |
|---|---|---|---|
| 本机中继 | ~0.7ms | 16 MB/s | ≈ 11 KB |
| 香港中继 | ~155ms | 50 KB/s | ≈ 8 KB |

**两种情况的在途量几乎相同（≈10 个包）**，吞吐比 ≈ RTT 反比（220x vs 320x，吻合）。
而 **10 个包正是 QUIC 的初始拥塞窗口**（RFC 9002 `10×max_datagram_size ≈ 12KB`）
⇒ **这条连接的拥塞窗口一直没涨起来（slow start 未推进）**。

本地因 RTT 极小，10 个包也能跑 16MB/s，所以**本地实验掩盖了这个问题**——
这点很重要，说明"本地测快了"不等于"代码没问题"。

对照：同链路 SSH(TCP) 有 600KB/s，因为 TCP 窗口会自动涨到 MB 级填满 BDP。

**下一步真正值得查的**（比"搬中继"更根本）：为什么 cwnd 不增长。
候选：中继链路丢包/排队让 QUIC 误判拥塞；或 QUIC-over-WS 某处缓冲过小。
若能让 cwnd 正常增长，不搬中继也能提速。

## ⚠️ 重要更正：上一节"瓶颈是链路"的结论**是错的**

用户质疑"延迟凭什么影响速度""顶级三网优化线路不可能成瓶颈""慢几百倍太扯"，
是对的。我做了同路径对照，结论推翻了上一节。

### 决定性证据：同一条路、同一个浏览器，普通 HTTP vs iroh

我在香港机上临时起了一个测速端点（`ufw allow 28901` + 一个 Python 收发服务，**测完已删除**），
用**同一个 Chrome** 测同一台服务器：

| 同一条路 | 吞吐 |
|---|---|
| 普通 HTTP **上传** 16MB | **630 KB/s** |
| iroh 经中继 | **30~50 KB/s** |

**12~20 倍差距。链路完全没问题，是 iroh 没用上带宽。**
（附带推翻：我沙箱里 curl 到 Cloudflare 只有 647~782 KB/s，而同一个 Chrome 有 1045~2146 KB/s
⇒ **我沙箱的网络比浏览器慢 2~3 倍，之前用 SSH 测的"链路基准 600KB/s"不可靠**。）

### iroh 侧的直接证据（`conn.stats()` 实测）

给发送循环加了 `conn.stats()` 采样（`transfer_orchestrator.rs`，每 128 块打一次）：

- **`lost_packets: 0, lost_bytes: 0`** —— **零丢包** ⇒ 拥塞控制不是因为丢包退让
- 写到 2MB 时 `udp_tx.bytes` 只有 **1.0MB** ⇒ **约 1MB 积压在发送队列** ⇒ 不是流控窗口太小
- 全程 `udp_tx.datagrams: 4359 / 195s` ≈ **22 包/秒** ⇒ **发包速率被限死**
- 传输期间香港机 `eth0` 只有 **~10 KB/s** ⇒ 数据确实没被送上网
- `frame_rx: ACK = 1`，但 **`PATH_ACK = 417`**（多路径专用帧）← 强烈可疑信号
- 多路径**无法关闭**：`max_concurrent_multipath_paths` 低于 `MAX_MULTIPATH_PATHS+1` 会被直接忽略

### 修正后的结论

**是 iroh（浏览器/wasm 侧）在"高 RTT + 中继"路径下的发包行为有问题**，
不是用户的网络、不是服务器、不是我们的应用代码。
本地中继（RTT≈0）同样代码 16 MB/s，说明代码路径本身能跑满。

**尚未查清**：发包为何被限住。已排除丢包与流控窗口；
最可疑是**多路径**（ACK 几乎都走 PATH_ACK，怀疑 cwnd 增长没被这些 ACK 驱动）。
下一步：让**原生客户端强制走中继**测一次 —— 若原生快、浏览器慢，就是 wasm 特有问题。

## ⚠️ 构建管线的静默失败（比速度问题更严重，已修）

**症状**：改 Rust、跑 `build-wasm.sh`、显示"完成"，但页面行为/日志格式还是旧的。

**根因**：脚本里是
```
ssh host "wasm-pack build ... 2>&1 | tail -20"
```
而**远程 shell 没开 `pipefail`** —— 管道的退出码取自 `tail`（永远 0），
于是**编译失败也被当成成功**，脚本继续把**上一轮的旧产物** scp 回来，还打印"完成"。
（真实案例：加了 RTT 采集后编译报 `PathList is not an iterator`，连续两次构建都"成功"了，
我对着旧 wasm 排查了半天。）

**修法**（`scripts/build-wasm.sh`）：
1. 远程命令前缀 `set -o pipefail`；
2. 拉回产物后**加断言**：`find src -name '*.rs' -newer pkg/*.wasm` 若有命中就报错退出。

**顺带**：`frontend/js/net.js` 的 `BUILD` 常量也要 bump（已 v7→v8），否则浏览器会命中旧 wasm。
不过这次真正的元凶是**磁盘上的产物就是旧的**，不是浏览器缓存 —— 别一上来就怀疑缓存。

## ⭐ 真正的机制找到了：QUIC 的 RTT 估计**涨到 1.8 秒**（bufferbloat）

修好构建管线、拿到真实 RTT 后：

| 采样点 | QUIC 测得 RTT |
|---|---|
| 第 0 块 | **180 ms** |
| 第 128 块 | **1807 ms** ← 涨了 10 倍 |

**吞吐 = 窗口 ÷ RTT**，RTT 涨到 1.8 秒，吞吐自然崩到几十 KB/s。
这是典型的**排队延迟（bufferbloat）**：数据在链路某个队列里堆积，
延迟越堆越高 → 窗口换算的吞吐越低 → 看起来像"被限速"。

**这解释了此前所有"矛盾"的现象**：
- 为什么**零丢包**却快不起来：不是丢包，是排队延迟；
- 为什么**发送队列积压 1MB**：数据推出去后堵在中间；
- 为什么**普通 HTTP 有 630KB/s**：TCP 的拥塞控制对这条路的队列反应不同；
- 为什么**本地中继 16MB/s**：本地没有队列可排。

**下一步（还在我们可控范围内）**：限制发送端"在途数据量"，
别把中间队列喂满。可试 iroh 的 transport config（`send_window` / `stream_receive_window`），
或减少单连接并发。**这是"我们没用对"最可能的落点，而不是上游的锅。**

## ⭐⭐ 根因确认（有上游来源）：CUBIC + 14.7KB 初始拥塞窗口

**从网上查到的两条决定性证据**：

1. **`n0-computer/iroh#4286`**：上游实测 **CUBIC 比 BBR 慢最多约 30 倍**
   —— noq/iroh 默认拥塞控制是**基于丢包的 CUBIC**，在高延迟链路上表现极差。
2. **iroh 官方基准**里 `iroh_relay_only 1_to_1 → 2.02 Gbps`
   —— 中继模式本身绝不慢，我们这 50KB/s 是**参数没用对**。
3. 源码确认：`noq_proto::congestion::Bbr3Config::default()`
   → `initial_window = 14720` 字节（≈10 个包）。
   **14720 B ÷ 0.28 s ≈ 52 KB/s —— 和我们实测的 50 KB/s 几乎完全一致。**

我之前实测"窗口卡在 ~10 个包"是对的，只是当时没意识到那正是**默认初始窗口**。

### 已实施的修复（`room.rs`）

```rust

bbr.initial_window(2 * 1024 * 1024);          // 14.7KB → 2MB
QuicTransportConfig::builder()
    .congestion_controller_factory(Arc::new(bbr))   // CUBIC → BBR3
    .build()
```
（Cargo.toml 新增直接依赖 `noq-proto = "1.3"`，因为 iroh 没重导出 congestion 模块。）

### 效果与仍未解决的部分

| 配置 | 8MB 实测 |
|---|---|
| CUBIC + 14.7KB（原始） | 38~55 KB/s |
| **BBR3 + 2MB** | **57~279 KB/s**（方差很大，最好一档 5 倍） |
| BBR3 + 512KB | 62 KB/s |
| BBR3 + 8MB | 65 KB/s |

### 下一步（按优先级）

## 追加：为什么会"锯齿"而不是一直占满带宽

用户看着系统网络监控问：为什么速率上下波动、不是一直跑满？

### 实测（真实拓扑，16MB）时间序列

500ms 分桶的速率：`480 → 768 → 800 → 640 → 0 → 0 → 736 → 32 → ...`
**峰值 1216 KB/s，但大量时间接近 0**，平均 434~478 KB/s。

### 原因：拥塞控制在"探测—填满队列—回退"之间循环

关键统计（真实拓扑）：

| 采样点 | RTT | 丢包 |
|---|---|---|
| 第 0 块 | 70 ms | 0 |
| 第 128 块 | **1925 ms** | 0 |
| 第 256 块 | **3498 ms** | 0 |
| 第 768 块 | 1692 ms | 0 |

**真实拓扑下零丢包**，但 RTT 一路冲到 3.5 秒 ⇒ **队列被灌满（bufferbloat）**，
主要堆在**客户端自己的上行缓冲**（ISP/路由器）——因为我们的发送速率超过了
上行真实容量（~630 KB/s）。BBR 看到 RTT 涨了就降速 → 队列排空 → RTT 回落 → 再加速 → 再灌满。

**所以锯齿是正常的拥塞控制行为**：能"一直占满"的前提是发送速率刚好等于瓶颈带宽，
而任何超发都会变成队列延迟。**平均 434~700 KB/s 已经贴着上行极限**，并没有浪费多少。

### 对比：同机拓扑会真的丢包

同机两标签（跨境两趟）时 `lost_packets` 从 0 涨到 **1711 → 2987**，
那是真的丢包（路径更窄、更挤），锯齿更凶。

### 可尝试的平滑手段（未验证）
- 把 `initial_window` 从 2MB 降到 256~512KB，减少超发（代价是起步慢一点）
- 但"平滑"和"峰值"往往互斥，需在真实拓扑下多测几次取中位数再定

## 更正："接收端滞后 1040 秒"是我的计算错误（问题不存在）

而邀请是在发送端重启后才广播的，接收端前面约 1050 秒在**空等**。

真实传输时长：发送端 469s vs 接收端 **458.6s**，**差 2%，两边完全一致**。
**不存在"发送完成后还要追很久"的问题。** 教训：打时间戳必须用"开始传输"为原点，
不能用"脚本启动"。

## 用户截图的 24.5/55 KB/s：拓扑 + 流量模型解释

同机两标签（A 发送、B 接收，都在用户 Mac 上）经香港中继的流量：

```
A → 香港：  上传数据      (占上行)
香港 → B：  下载数据      (占下行)
B → 香港：  ACK          (占上行)  ← 抢上行
香港 → A：  ACK          (占下行)
```
**同一份数据在网络上走了两趟**（出境再入境），有效速率 ≈ min(上传, 下载)。

真实两用户（各一台机器）：
```
A 机器：上行=数据+ACK，下行=ACK
B 机器：上行=ACK，下行=数据+ACK      ← 数据只跨境一趟
```

实测对照（同样代码）：
- 同机两标签：85~190 KB/s
- 真实两机：**825 KB/s**（用用户的真实 377.9MB 文件测出）

→ 结论：截图的低速是**测试方式**造成的，不是产品问题。

## 🎯 找到"55 KB/s"的真凶：**Chrome 后台标签页定时器节流**

### 硬证据（直接测量）

在页面里跑 `setTimeout(f, 20)` 并记录真实间隔：

| 页面状态 | 实测间隔 |
|---|---|
| **前台** | **21~23 ms** ✅ |
| **后台 40 秒后**（`document.hidden = true`） | **998~1001 ms** ❌ |

**Chrome 把后台标签页的定时器压慢了约 50 倍。**

### 为什么这能解释一切

iroh 的 QUIC 栈**完全靠 `setTimeout` 驱动**
（`n0-future` 的 wasm 定时器实现就是调 `setTimeout`）——
发送节奏、ACK 处理、丢包检测、拥塞窗口推进全都挂在它上面。
**定时器慢 50 倍 ⇒ 吞吐掉到 1/50。**

用户截图里的 24.5/55 KB/s 正好在这个量级。

### 完整因果

```
点"接收" → 切去别的标签页 → Chrome 隐藏 >30s
  → 定时器 20ms→1000ms → QUIC 定时器被拖垮 → 24.5/55 KB/s
```

**我自动化测试测不出这个问题**，因为无头 Chrome 的标签一直是"活跃"的。

### 影响

| 场景 | 影响 |
|---|---|
| 盯着页面看 | ✅ 800+ KB/s |
| **切走 / 最小化** | ❌ 掉到 1/50 |

**没人会盯着进度条看 8 分钟，所以这是真实产品问题。**

3. AudioContext 静音保活（业界常用，略流氓）
4. **后台自动暂停 + 回来续传**（断点续传已具备，成本低、体验好）⭐ 倾向先做这个

## Web Worker 方案可行性：已实测验证 ✅

用户问"传到 Worker 是不是多了一跳（本机→Worker→服务器）"——**这是误解，Worker 不是另一台机器**。

### 澄清：Web Worker ≠ Cloudflare Worker

| | Web Worker | Cloudflare Worker |
|---|---|---|
| 位置 | **用户浏览器里**的一个线程 | CF 的服务器上 |
| 性质 | HTML5 标准（2009） | 无服务器后端（2017） |
| 目的 | 不卡界面 / 绕过后台节流 | 免运维后端 |

**Worker 与主线程同进程、共享内存，网络连接只有一条**，端口路径完全不变。

### 实测 1：Worker 里能完整跑 iroh ✅

```
✅ EndpointId: bdbacbaa90c33718...
   加载 wasm 21ms | 初始化 14ms | 启动 2ms | 连上中继 2810ms
```
（注意：blob Worker 里必须用**绝对 URL** `self.location.origin + '/pkg/...'`，
相对路径会报 `Failed to resolve module specifier`。）

### 实测 2：数据"过 Worker"零成本 ✅

2000 次 × 16KB（= 64MB 的块数）：

| 方式 | 总耗时 |
|---|---|
| `transfer`（零拷贝移交） | 9376 ms |
| 普通拷贝 | 9370 ms |

**差 0.06%，且这 9.4 秒几乎全是脚本里 `setTimeout(0)` 的等待**——真实传递成本测不出来。
（`postMessage` 传 `ArrayBuffer` 走 Transferable，是指针移交，不拷贝字节。）

### Worker 改造的真实风险点（不是"多一跳"，而是这些）

1. **每块一次 postMessage 往返**可能成新瓶颈（读写回调原本是同步调用）
2. **`showSaveFilePicker` 的句柄不能跨线程**，接收侧要在 Worker 里调（需用户手势 → 从 UI 转发）
3. wasm endpoint 生命周期、事件流、UI 交互全部要改

→ 真要做得先量化第 1 条，或改用 `SharedArrayBuffer`（需 COOP/COEP 响应头）。

## 方案取舍：为什么"优雅暂停"不存在

### 试过的三个思路，两个被否决

1. **❌ 静音音频保活**：A/B 实测无效（Chrome 只豁免可听见的媒体）。已撤代码。
2. **❌ 软暂停（靠流控背压）**：暂停时发送方阻塞在 `write_all`、
   连接上零流量，而 iroh 默认 `max_idle_timeout = 30 秒`
   → **暂停超 30 秒连接就被掐断**，回来还得重连，
   等于绕回"中断+续传"，没有更优雅。
   （而且暂停场景恰恰是"定时器被节流"，连 keep-alive 都发不准。）
3. **✅ 只剩两条路**：
   - **A. 后台中断 + 回来自动续传**：不改协议，复用现有 `abort`（存位图）+ 重 `accept`。
     解决"以为在传、其实龟速"的困惑；**不能**让你切走后还全速传。
   - **B. Web Worker**：唯一能"切走仍全速"的方案（Worker 定时器实测不受节流）。

### 实验尝试记录（避免后人重复）

为了量化"后台到底掉多少"，我试了 5 次搭"香港 Chrome + 香港发送端 + SSH 隧道"的三体环境，
**每次都在组件时序上卡住**（邀请过期 / 隧道只转发 9333 导致页面加载不了前端 / 进程被中断）。
结论：**这个量化不值得继续投入**，因为"定时器 50 倍降速"是已直接测出的硬事实，
机制链完整（QUIC 依赖 setTimeout 是源码确认的）。

## 方案 A 落地：后台自动暂停（含一次失败尝试的记录）

### 最终交付的形态

**已上线**：切到后台超过 **3 秒**（宽限期，避免频繁切换断连）→
自动暂停接收（走 `abort` 路径：`close(writable)` 提交已写内容 + 存位图）
→ 回到前台提示"请重新点击接收继续（会从断点续传）"。

**回归测试 6/6 通过**；真机验证（真实切标签页，64MB）：
```
前台 active 84 块 → 切后台 3s 后状态转 failed（暂停生效，967/4096 停下）
                → 回前台仍 failed，等用户手动续
```
（后台 3~12s 期间块数仍在涨，是 wasm 侧通道里已缓冲的块在陆续落盘；
那些块都正常写入并被位图记录，不会丢。）

### ⚠️ 失败尝试：自动续传会把文件写坏（已回退）

试过"回到前台自动重跑 `accept()`"，实测 **块数翻倍、文件写坏**（8MB 收成 1024/512）。

**根因在 wasm 侧**：`abort()` 只让 JS 停止处理，
而 `FileService::accept()` 的读流循环**仍在把块推进通道**；
新一轮 `accept()` 又登记一条新记录 ⇒ **新旧两条链路并行写同一个文件**。

**正确的修法**（未做）：给 wasm 加 `FileService::cancel(file_id)`，
让读流循环真正退出、丢掉通道，再重连。
**在没做完之前不启用自动续传** —— 宁可让用户手动再点一次"接收"
（走已充分验证的断点续传），也不要静默把文件写坏。

**教训**：我中途用"代号(gen)拦住旧回调"的办法试图绕过，
但拦不住 wasm 侧的写入调用 —— **在错误的层次打补丁，治不了根**。
察觉到数据被写坏后立刻回退，这是对的。

### 用户澄清的一个概念误解

用户以为"Worker"是 Cloudflare Worker（后端 serverless）。
**Web Worker 是浏览器里的线程**（HTML5，2009），与 CF Worker（2017）无关，
只是名字撞车。Worker 与主线程同进程、共享内存，**网络只有一条连接，不是多一跳**。
