# 2026-10-03

## 修掉一个真实产品缺陷：广播串扰劫持旁观者的文件卡片

### 现象
C 点了聊天记录里的文件卡片 → 发送方重发邀约（**广播给全房间**）→
连**从没点过**的旁观者 D 也被塞了一张 `invited` 卡片。

### 为什么是真 bug（不只是"多一张卡"）
`_refreshArchived()` 只处理 `archived` / `asking` 状态。卡片一旦被改成 `invited`，
就**再也不参与可用性计算** —— 发送方刷新后它永远不会显示"已过期"。
实测：线上端到端里 D 的 `avail` 恒为 `null`，成员表 5→4 正常掉人但卡片永远不态变。

### 修法（frontend/js/ui/filetransfer.js）
1. `_onInvite()`：已有卡片是 `archived` 时**直接 return**，不覆盖。
   点击者自己的卡片在 `openArchived()` 里已被置为 `asking`，由下面分支正常接管。
2. `_refreshArchived()`：把 `invited` 也纳入可用性计算 —— 那种卡片同样是
   "别人点卡片时被广播进来的"，发送方刷新后也该标"发送方已离开"，
   而不是永远停在一个点不动就点不动的假"待确认"。
   `invited → expired` 时要 `forgetInvite(id)`，否则刷新后又被恢复出来。
3. 顺带清掉 792-793 行的冗余判断（792 已排除 `asking`，793 永不可达）。

### 测试
- `/tmp/file-history-test.py` 加了 2 条断言，并把 **D 的进房时序提前到 C 点接收之前**
  （原来的顺序让 D 在 C 点完才进房，压根测不到串扰）。
  现在 16/16；其余回归 review-frontend 19、dm-removed 14、stale 4、
  offline-room 4、refresh 4 全过。
- 线上 `/tmp/bu-e2e2.sh` 10/10（D 全程 `archived`，41.8s 变过期）。

## browser-use 端到端调试的四个坑（都曾导致误报）

1. **`__clearBitmaps()` 里有 `transfers.clear()`** —— 必须在**收到邀约之前**调，
   否则它把刚到的邀约卡片自己抹了，`__acceptFile` 无从下手，
   表现为「B 永远停在 invited」。踩过一次。
2. **`js()` 默认 `awaitPromise`** —— `window.__openRoom(r)` 要真进房（>5s）
   会被 harness 掐断。必须"点火就走"：`(() => { window.__openRoom(r); return 1; })()`。
3. **heredoc 必须用 `<<'PY'`** —— 否则 bash 对 Python 体做命令替换，
   `$(...)`/反引号被吃掉，报莫名其妙的 "syntax error"。
4. **必须带 `&testid=1`** —— 不带时同一浏览器多个标签页拿到**同一身份**
   （`myId` 相同），表现得像"文件传不过去"。
   另外 `?key=<64hex>` 才是固定身份（`testid` 每次都随机）。

## 一个测试自身的缺陷（值得记住）
验证"发送方刷新后文件过期"时，**不能用已收完的接收方当断言对象** ——
文件已经在它磁盘上了，不该受影响。需要另开一个"只看不收"的旁观者。
同理验证"点击能拿到邀约"要在**发送方还在线时**做；
放到"发送方已刷新"之后做，那必然失败（这本身就是"确实不可接收"的正面证据，
但不能当成"点击功能正常"的证据）。

## 结果：17/17 + 1/1 全部挡住，但过程中抓到两个真问题

### ① `HistoryStore::append` 的内存路径没验签（攻击 2 第一次跑就失败）
- 现象：拿有效消息**改掉 id** 后塞进 `append`，内存计数变成 2（凭空多一条发言）。
- 根因：`append` 信任调用方已验签，自己只按 `id` 去重。
- **修法**：`append` 自己兜底验签，返回 `bool`；失败打 warn 并拒绝。
  roomd 调用点简化为 `let _ = store.append(...)`（不再重复验签）。
- 理由：历史是**持久化**的，一旦写进去每次重启都会加载出来。
  把校验放在调用方，只要有一条路径忘了验证，脏数据就永久留下。
  ed25519 验签 ~50µs，这个兜底很便宜。

### ② 拒绝文件流时对端只看到 `connection lost`（攻击 3' 暴露）
- 现象：冒充者被拒后读到的是 `connection lost`，**拿不到拒绝原因**。
- 根因：拒绝分支 `write_json_frame` 完直接 `return Ok(())`，
  `send`/`recv` 随函数返回一起 drop → QUIC 连接被带走。
- **修法**：抽出 `deny(send, recv, reason)`：写回执 → `finish()` →
  **等对端读完**（最多 2 秒）→ 再返回。三处拒绝统一走它。
- 意义：对端能区分"我是被拒了"还是"网络抖了"，不用盲目重试。

## 攻击脚本自身的两个坑（都曾误判成"修复失败"）

1. **冒充者不能写完帧就 `outgoing.finish()`** —— 半关闭抢在服务端写回执之前断开。
   真实攻击者会等回执判断成败，脚本也应如此（改成"先读回执再关"）。
2. 断言失败要打印**实际收到的内容**（ack / 计数），否则只能猜。

## 这一轮踩/学到的坑

1. **zsh 里 `path` 是绑定 `PATH` 的特殊数组** —— 我用 `for path in ...` 当循环变量，
   赋值直接把 `PATH` 毁了，后续 `env`/`head`/`tr` 全报 command not found。
   **循环变量别用 `path`**（同理别用 `path`、`cdpath`、`fpath`）。
2. **后台进程活不过一个回合**：`nohup ... &` 在 Bash 工具里起的 Chrome/服务，
   回合一结束就被回收（Chrome 日志 `parent died?`）。要用
   **`run_in_background: true`** 启动，才能跨回合存活。
3. **Chrome 必须 `--no-sandbox`**：本环境里它自带沙箱初始化失败
   （`sandbox initialization failed: Operation not permitted`）会让主进程退出；
   加 `--no-sandbox --disable-setuid-sandbox` 才稳。
4. **沙箱代理会给 HTTPS 做中间人**（自签证书）→ 从本机 curl 线上站点报
   `SSL certificate problem: self signed certificate`，`-k` 也不行。
   **改用构建机 curl 比对哈希**（真实网络、无 MITM）；顺带记：`curl -o` 失败时
   不会清空旧文件，容易把"上次的残留"当成"线上内容"（这次先误判了一次）。
5. `/index.html` 返回 **307**（Cloudflare 规范化到 `/`），是正常的，不是部署失败。
