## 状态页/设置页：核实"配置是否真实可用" + UI 打磨

用户问「这两页的配置都是真实可用的吗」，并说「UI 和交互还是有点粗糙」。

### 核实结论：数据都是真的，但有 3 处"看着真、其实没接线"

**真实**（逐项查了消费方）：状态页的节点态/中继/延迟/邻居/身份全部来自真实数据源
（`EV.NODE_STATE`、`EV.RELAYS` 缓存快照、`net.probes`、`PEER_UP/DOWN`）；
设置页的昵称、发送快捷键、主题、消息密度、导出、清本地、换密钥、清空全部都是真动作。

**假的三处**：
1. **设置页资料卡的「复制」按钮从未被绑定** —— bind 的选择器是
   `.set-row[data-act]`，而这个 `<button>` 在 `.set-card__id` 里（不是 `.set-row`）
   → 点了完全没反应。改用 `[data-act]`。
2. **「未读时闪烁标题」是空开关** —— `paintBadge` 无条件写 `document.title`，
   这个 pref 存了值却没有任何读取方（复检报告 P3-11 早已点名，一直没修）。
3. **提示音开关是真的，但声音是哑的** —— `new AudioContext()` 在没有用户手势时
   创建出来就是 `suspended`，而 `ding()` 遇到 suspended 直接 return。
   → 在第一次 pointerdown/keydown 时 `resume()`。

### 中继能否手动切换 → 不能直接切，但可以"排除"

中继来自 `frontend/relay-config.json`（hk-1 / eu-1 / fr-1）。
**选哪台由 iroh 内核自己决定**，已在 vendored 源码 `iroh-1.3.0/src/net_report.rs:763-817` 核实：

- 按**最近 5 分钟**（`MAX_AGE`）每台的最低延迟选 `preferred_relay`
- 有**滞后（防抖）**：老的那台还通、且新台延迟没优于老台的 2/3 时，**不换**
  （`best_any > old_relay_cur_latency / 3 * 2` → 保持原样）

UI 的「重新探测中继」走的是自己的 HTTP `/ping`（`probe.js`），
**与内核的 net_report 是两套独立测量**，前者只用于显示，不喂给选路。

想手动干预只能改配置里的 `enabled`。**而这个字段原本是坏的**（本轮修了）：

- `probe.js` 按 `enabled !== false` 过滤，`net.js` 却把全部 url 丢给 Rust，
  而 **Rust 侧没有任何 enabled 概念** → 设 `false` 照样被选
- 修法：`net.js` boot 前过滤；一台不剩时报明确错误
- 状态页如实标「已禁用」并压淡（写"未使用"是在暗示它随时可用）

## 追问：两个用户用不同中继会有影响吗 —— 实测

**不能靠推理答，我造了跨中继场景实测**（起第二个站点只放行指定的中继，
用 `serve-dir.py` + 软链，改 `/tmp/site-eu/relay-config.json` 控制它的名单）。

### 结论一：**普通用户之间，不同中继没有任何影响**

最严苛的组合也通了：A 名单 `[hk-1,eu-1]` 落 `eu-1`，B 名单 `[hk-1,fr-1]` 落 `fr-1`
—— **双方名单里都没有对方所在的中继** —— 仍然 3 秒互相看见、双向消息各 1.5 秒送达。

iroh 按最近 5 分钟延迟自动选 home relay，所以"不同人落在不同中继"是**常态**。

### 结论二：**名单里必须包含「常驻节点当前所在的中继」**（现在是 hk-1）

| 名单 | 结果 |
|---|---|
| 三台全放行（默认） | ✅ 进房 |
| 只有 hk-1 | ✅ 进房 |
| 只有 eu-1 / 只有 fr-1 | ❌ 95~100s 进不去 |
| eu-1 + fr-1（**无 hk-1**） | ❌ 95s 进不去 |
| eu-1 + fr-1 + hk-1 | ✅ 进房 |

最后一组是对照，证明原因是**缺 hk-1**，不是"名单只有一台"。

失败形态很坑：**没有明确报错**，只是 `joined` 一直为 null。
因为 `join()` 的流程是「10s 敲锚点（失败只 warn）→ `subscribe_and_join` 重试 4×20s」，
所以至少要 90 秒才失败 —— 我一开始 40 秒就放弃，误以为是别的问题。

### 附带发现

- **iroh 选路有随机性**：同一配置同一机器，实测分别落到 eu-1 / hk-1 / fr-1。

    `align-content: center`** —— 默认 stretch 会把 logo 和文案撑开到整个高度、上下分离

## 调研 + 设计：消息存储方案（用户对"历史存服务端"有顾虑）

产出 `docs/message-storage-design.md`。用户问的是"要不要照微信改成端侧存储"。

### 三个必须记住的事实（前两条与直觉相反）

**1. ⚠️ 本项目没有加密，只有签名。**
`ChatMessage.text` 是**明文**，全仓 `grep -i "encrypt|decrypt|cipher|aead"` 为空。
所以"把历史放服务端"确实多一个副本，但**不是"加密 vs 不加密"的差别** ——
**中继本来就看得见全部明文**。要"服务端拿不到内容"得加 E2EE，是另一个课题。
（附带：`topic = blake3(命名空间 + 房间名)`，**房间名可枚举**，
严格说不是"知道房间名才能进"而是"猜得到就能进"。）

**2. ⚠️ 微信群聊"退出期间收不到消息"是误传。**
腾讯客服口径：**未接收的消息服务器保留 3 天**，3 天内登录可补，超期永久丢失。
微信真实模型 =「服务器不存历史 + 存 3 天未送达消息 + 客户端存全部」。
注意区分"未接收"和"已接收未读"——留 3 天的是前者。

**3. 微信群新成员看不到加入前的历史**（与"记录只在设备本地"自洽），
只能靠群成员人工转发，**上限 99 条**。

### 本项目现状（已核实）

- **客户端零消息存储**：IndexedDB 那个库叫 `iroh-transfers`、store 叫 `bitmaps`，
  **只存文件传输位图**（断点续传用），不存任何聊天消息
- 服务端权威：roomd 落盘 `data/history/*.jsonl`；
  上限 5000 条 / 16 MiB 内存、64 MiB 磁盘；前端分页 50 条/页
- 与本项目相比，微信正好**反过来**：微信=客户端权威 + 服务端 3 天缓冲

### 建议：**不要照搬微信**

微信那套是被 13 亿用户的规模成本逼出来的，不是最优设计
（换手机丢历史、新成员看不到历史、3 天不登录永久丢消息 —— 这些是**缺陷不是特性**）。
照搬的后果是**刷新页面 = 历史清零**（浏览器 IndexedDB 没有 SQLite 那种强保证），
比现状明显退步，理由却只是"像微信"。**该模仿的是交互，不是存储实现。**

若要更像微信，给了三档，推荐**档位 A**（性价比最高）：
给房间加 `history_visibility`（照搬 Matrix 语义），默认 `joined` = 只看加入之后。
服务端记 `firstSeenMs`、拉历史时截断 —— **不动协议、不动客户端、可回退**。
诚实边界：这是服务端过滤，防普通用户，防不住直连 roomd 的人。

端侧 IndexedDB 只做**缓存**（加速首屏），**不能做权威**（否则掉进"换设备丢历史"）；
localStorage 不适合存消息（~5 MB、同步阻塞、只存字符串）。
Matrix 的 `useIndexedDB` 默认 true，但官方明确它只是缓存、让"不必完整 sync 一次"。

### 附带指出一个更紧急的问题

**历史 ALPN 无应用层鉴权**，房间名是唯一凭据且可枚举 ——
**现在任何人猜到房间名就能读走该房间全部历史**。
这比"历史存哪"严重得多，提升隐私应**优先修鉴权**，而不是搬存储位置。
