# 2026-09-29

## iroh 浏览器聊天室方案调研（产出：docs/iroh-chatroom-feasibility.md）

用户构想：iroh 聊天室，前端部署 Cloudflare，iroh 节点可在页面配置；在每台（会频繁更换的）服务器上部署 iroh 中继，
前端识别各中继连接状态与质量并据此选择中继信道。

### 调研得到的关键结论（后续开发直接依赖这些事实，勿重复调研）
- iroh 1.0.0 于 2026-06-15 稳定，**当前最新 1.3.0**；wasm/wire 稳定承诺只覆盖 v1，别再 pin 0.9x/RC。
- **浏览器 WASM 端点永久 relay-only**：不能发 UDP → 无法打洞，100% 流量经中继（官方明文）。官方无 npm 包，
  必须自建 wasm-bindgen wrapper crate；需 `iroh = {version="1", default-features=false}`。
- iroh-relay：HTTPS 443 上跑 WebSocket 中继协议，UDP 7842 跑 QUIC 地址发现（QAD）；无状态、可自托管、
  内建 ACME/手动证书、支持 shared_token 和 **HTTP callout 鉴权**（可指向 Cloudflare Worker）。
- **中继选择是 iroh 内核做的**：启动时对 RelayMap 全部中继做延迟探测（QAD 优先，HTTPS probe 延迟 200ms 兜底），
  选延迟最低者为 home relay。可观测 API：`home_relay_status()`（last_error / auth_denied_reason）、
  `net_report()`（unstable feature，含 relay_latency）、`online()`；运行期可 `insert_relay` / `remove_relay`。
- **关键架构纠正**：被中继的流量走"对端广播的 home relay"，中继之间不互转 → 想要"一个房间一条中继信道"必须
  全网单中继配置（牺牲容灾），否则连接数膨胀。此点官方未明文，已列为 spike 必验证项。
- relay protocol v2 版本兼容单向：老客户端能连新中继，新客户端连不上老中继 → 换服务器必须"先升中继再发前端"。
- **Cloudflare 只能做控制面**：Workers 运行时无 UDP / 无 WebTransport / 无入站 TCP，跑不了 iroh 节点和原生中继；
  中继也不能挂 Cloudflare 代理（7842/UDP 过不去）。正确分工：Pages 托管前端 + Worker 下发中继名单 + Worker 做中继鉴权 callout。

## 【实测】服务器 189.24.68.147 部署 iroh-relay 1.3.0 + 多中继语义实验

### 服务器与访问
- `ssh -i /Users/patrick/Desktop/ssh/mindcrew/codex -p 15601 root@189.24.68.147`（Ubuntu 22.04，8C/16G，公网直连无 NAT）
- 该机是 **1Panel 生产机**：OpenResty 占 80/443(TCP 与 UDP/443)，28 个 Docker 容器（mindcrew / WeKnora / sub2api / dpxwebsite 等）。
  **不要动 openresty 配置**；可用空闲端口 3340/3341/7842/8443。
- 已部署：`/usr/local/bin/iroh-relay`（1.3.0 musl 静态），systemd 模板单元 `iroh-relay@a`(:3340) / `iroh-relay@b`(:3341)，
  配置在 `/etc/iroh-relay/relay-{a,b}.toml`，纯 HTTP、`access = "everyone"`（测试用，未加鉴权）、每客户端限速 2MiB/s。
  ufw 已放行 3340/tcp、3341/tcp、7842/udp。部署脚本可复用：`deploy/relay/`（含 README + 幂等安装 + 两个实验脚本）。

### 实测结论（推翻了我此前的一处推测，报告 §8.3 有完整矩阵）
1. **中继之间不互转**：拨号方被指向"对端不在这台"的中继 → 13s 超时失败，**即使那台中继在拨号方的 RelayMap 里**（E4 失败）。
   → 生产必须保证拿到对端**正确且最新**的 home relay 地址，否则"双方都在线却连不上"。
2. **对端的中继不必在自己的 RelayMap 里**：E3（dialer map=[b]，指向 a）**成功**。约束是"URL 正确"，不是"名单一致"。
3. 空闲时客户端只维持 **到 home relay 一条连接**（另一个候选中继无连接）。
4. **故障自动切换可用**：候选 [a,b]，停掉 a 后 25s 内自动切到 b，恢复后自动连回，应用层零重试。← 对"频繁换服务器"价值极高。
5. 延迟：探测机 → 该中继 TCP connect 38–62ms，TTFB 82–115ms。
6. 中继自带 Prometheus 指标（`relayserver_bytes_*` / `send_packets_*` / `accepts_total` / `unique_client_keys_total` / `qad_*`），
   `metrics_bind_addr` 默认在 127.0.0.1:9090，实测可用作服务端健康度面板数据源。

### 坑（下次直接用）
- `iroh-relay` 默认绑 `[::]:80`，配了 `http_bind_addr` 才不会撞 nginx。
- `enable_quic_addr_discovery=true` 必须同时有 `[tls]`，否则启动失败；`--dev` 模式与 TLS 互斥且没有 QAD。
- **`iroh-doctor 0.101.0` 预编译二进制 TLS 已坏**（`No rustls crypto provider configured`），只能测纯 HTTP 中继；
  要测 HTTPS/QAD 必须自己编 `iroh = "1.3"` 客户端。
- 在 ssh 一行命令里用 `pkill -f "iroh-doctor --config"` 会**连自己的 shell 一起杀**（cmdline 含同名字符串）→ 用 `iroh-[d]octor`。
- macOS 无 `timeout` 命令；本沙箱会 SIGTERM 掉需要开 UDP 的网络二进制（doctor 在本机跑不起来，改到服务器跑）。
- GitHub 大文件在本机沙箱常断（HTTP2 framing / CONNECT 502）→ 改从服务器下载再 scp 回来。

### 协议细节（写客户端/探测必须知道，实测）
- `/relay` 的 WebSocket 升级**必须带 `Sec-WebSocket-Protocol: iroh-relay-v2`**，否则 **400 Bad Request**。
- 鉴权头是 `x-iroh-relay-client-auth-v1`，**浏览器设不了自定义 header → 走 URL query `?token=`**。
- `/ping` 是延迟探测端点；**配置 `[tls]` 后 `http_bind_addr` 的明文口不再是 relay**（healthz 返回 404）。
- `/ping` 处理开销可忽略（复用连接后 0.1–0.3ms），但**新建 TLS 连接付 2–3 RTT**：
  香港→欧洲 新建 754ms vs 复用后真实 233ms（ICMP 250ms）→ 探测必须先预热、读
  `PerformanceResourceTiming.requestStart→responseStart`。

### 延迟基线
- 香港 ↔ 欧洲 ICMP ≈ 250ms；香港 → iroh2 复用后 233ms；香港 → iroh1 ≈ 0.1ms（本机）。
- 探测机(Mac，疑似走代理) → iroh1 233ms(fresh) / iroh2 743ms(fresh)。
- 结论：香港/中国大陆用户会被 iroh 自动选到 iroh1，"按延迟择优"符合预期。

## 【证书能力与方案修正】2026-09-29 夜

### 用户提问引发的重要修正
用户问"cert_mode=Reloading 是什么意思，中继本身就有签发证书功能吗"，并指出"我有多个服务器，不是每个都有 1Panel"。
→ 实测后**修正了上一轮的说法**（之前说"Reloading 与 1Panel 不兼容所以不能用"是错了一半）：

| cert_mode | 谁签发 | 实测结果 |
|---|---|---|
| `LetsEncrypt` | **中继自己（内置 ACME 客户端）** | ✅ 流程真实走通：连上 ACME、创建账号缓存、监听 80 做 HTTP-01；我用保留域名邮箱被 LE 以 `invalidContact` 拒 → 证明只差一个合法邮箱 |
| `Manual` | 外部 | ✅ 可用，换证书要重启 |
| `Reloading` | 外部 | ✅ **期望文件名 = `default.crt` + `default.key`**（在 cert_dir 下）；1Panel 输出的 fullchain.pem/privkey.pem 名字对不上才会失败 |

- **结论：Reloading 两种场景都能用**，只要把外部签发的证书改名复制成 `default.crt/default.key` → **续期零重启**。
- 中继自带签发的代价：**80 端口被中继长期占用**（做挑战与续期），该机不能再放网站。
- 关键前提：`LetsEncrypt` 需要域名 + 合法邮箱 + 80 空闲；`Reloading`/`Manual` 需要外部工具先签好。

### 交付物更新

## 【鉴权 saga 彻底解决】2026-09-29 21:35

### 最终根因（一个，非常隐蔽）
**`docker compose up -d --force-recreate` 只重建容器、不重建镜像；而 Dockerfile 里是 `COPY roomd`，
二进制被"烤"进镜像。** 所以我改了源码 → 编译了新二进制 → 覆盖磁盘上的文件 → `--force-recreate` N 次，
**跑的始终是镜像里的旧程序**（中继日志里它是"被拒"，因为旧程序没有 token 注入）。

铁证：`docker exec roomd md5sum /usr/local/bin/roomd` = `ffcdfec5…`（旧）
vs 磁盘 `/opt/iroh/roomd/roomd` = `fd576e1f…`（新）。
→ **必须 `docker compose build --no-cache && docker compose up -d`**（或 `docker compose up -d --build`）。

### 排查过程中挖出的 debug 日志方式（关键技巧）
`compose` 里硬编码的 `RUST_LOG=info` 会**覆盖 `.env`** → 必须先改成 `RUST_LOG=${RUST_LOG:-info}`，
再在 `.env` 里设 `RUST_LOG=info,iroh=debug,iroh_relay=debug,iroh_gossip=debug`。
然后就能看到决定性一行：
`dialing: Dialing relay by websocket dial_url=wss://iroh1.editor.vip:15443/relay`（**没有 ?token=**）。

### 修复后完整验收（浏览器，鉴权开启）

### 滚动 bug 根因（经典 CSS 陷阱）
flex/grid 子项默认 `min-height: auto`（不许小于内容高度）。`.chat` 是 grid 子项，

**修法**：从根到可滚动元素的**每一环**都要 `min-height: 0`，grid 列要用 `minmax(0, 1fr)`
（`1fr` 的最小宽度是 auto，长消息会撑宽列）。已写进 `css/layout.css` 的注释里。
关键指标：`timelineH: 638`（原来是 0）、`timelineScrollable: true`、`composerInViewport: true`。

## 【消息大小上限：真实限制 & 修对】2026-09-29 23:30

### 用户提问
"这里为什么限制文件大小？iroh 还限制文件大小吗" —— 我界面写的"上限 180KB"被质疑。

### 真相（源码确认，我原来的数字是瞎写的）
`iroh-gossip` 有真实限制，**默认 4096 字节**：
```rust
// iroh-gossip/src/proto.rs
pub const DEFAULT_MAX_MESSAGE_SIZE: usize = 4096;
pub const MIN_MAX_MESSAGE_SIZE: usize = 512;
```
**但它可配置**：`Gossip::builder().max_message_size(n).spawn(endpoint)`。
→ 我原来那个"180KB"**没有任何依据**，纯属编的。

### 改法
- `client-wasm/src/room.rs`：新增 `pub const MAX_MESSAGE_SIZE: usize = 512 * 1024;`（512KB），
  在 `RoomNode::start` 里 `.max_message_size(MAX_MESSAGE_SIZE)`
- `client-wasm/src/bin/roomd.rs`：同样设置（保持与客户端一致，否则常驻节点收不下大消息）
- 前端 `js/ui/composer.js` 的 `MAX_INLINE` 同步为 512KB，并把弹窗文案讲清楚
  「消息通道是广播的，一条消息会发给房间里每个人，所以不适合传大文件；大文件应走对象存储 + 链接」

### 实测（原生 roomtest，新增 ROOMTEST_BIG_KB 环境变量）
```
=== 大消息测试：300KB ===
✅ 300KB 发送成功，耗时 2.643ms
✅ 历史里能查到这条大消息（长度 307200 字节）
```
→ 300KB 完整送达、未被截断，且经过常驻节点（说明中继+锚点全链路都吃下了）。

### 第二个问题：那个"太阳"图标
**不是主题图标，是「设置」标签的图标被我画成了太阳**（圆 + 8 条放射线 = 太阳形状）。
主题切换图标（列表右上角）逻辑本身是对的：深色显示月亮、浅色显示太阳。
→ 已把设置图标换成**真正的齿轮**（带齿外轮廓 + 中心圆）。

### 重要教训
**不要在 UI 上写没有依据的数字。** 我编的 180KB 导致用户以为"iroh 只能传 180KB"，
实际官方默认是 4KB（我写大了），而真实可配置到 512KB+（我写小了）。
涉及"能力边界"的数字，必须去源码确认。

## 【P2P 文件传输：协议层完成】2026-09-29 23:50

### 用户的决定（三条，务必按此实现）
1. **默认 stream 模式**（QUIC 流 + 边收边写盘，支持 10GB），设置里可切 **blobs 模式**
   （用 `iroh-blobs`，快但受 wasm 内存上限约束，<4GB）→ **两种都要实现**
2. **断点续传一开始就要**
3. **Firefox / Safari 直接禁用发文件**（PC 为主）
4. **块清单存 IndexedDB**（刷新不丢，能隔天续传）

### 为什么不用 iroh-blobs 直接传（查证结论，重要）
- `iroh-blobs` 0.103 的 `store` 模块只有 `fs`（原生）/ `mem` / `readonly_mem`，**浏览器里只有 MemStore**
- 官方 `browser-blobs` 示例（前端仅 80 行）的做法是
  `download()` → 整个文件进 wasm 内存 → `get()` 再拷到 JS 堆 → `TextDecoder`。
  **它只传了个小字符串**，不是大文件方案
- wasm32 地址空间上限 4GB（实际 1~2GB 就不稳）→ **10GB 不可能走 MemStore**
- 结论：**借用 iroh-blobs 的格式（blake3 + 16KB 块）**，数据面走自己的流式管道

### 已实现：`client-wasm/src/filetransfer.rs`
- **控制面（走 gossip，只带元信息）**：`SignedCtrl{Invite|Accept{have,receiver_relay}|Reject|Done}`，
  ed25519 签名 + `canonical()` 规范化串（`f1|invite|...` / `f1|accept|...`）
- **数据面**：独立 ALPN `editor.vip/iroh-file/1`，**发送方拨号**（因为中继不互转，
  必须从 Accept 里拿 `receiver_relay`）；帧格式 `[u8 kind][u32 len BE][payload]`
  - `kind=1` header（JSON）/ `kind=2` chunk（`[u32 seq BE][原始字节]`）/ `kind=3` done（JSON）
- **接收服务** `FileService`：按 `file_id` 把流派发给上层预先登记的 channel
  （上层在发 `Accept` **之前**必须 `expect()`，否则数据会丢）
- **断点续传基础**：位图 `bitmap_new/get/set/count_set/to_b64/from_b64/resize` +
  `missing_chunks()` 算需要补发的块
- 工具：自带 base64 / hex 实现（不引额外依赖）、`chunk_count` / `chunk_range` / `human_size`
- `CHUNK_SIZE = 16 KiB`（与 iroh-blobs 的 `IROH_BLOCK_SIZE` 一致）；`MAX_FRAME = 1MB` 防打爆内存
