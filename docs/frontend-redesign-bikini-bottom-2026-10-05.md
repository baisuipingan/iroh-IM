## 0. 一句话结论

**设计稿是一套「视觉语言 + 交互演出」规范，不是功能规格。**
它只覆盖了现有前端功能的约一半（会话列表 + 对话区 + 输入区 + 新建房间），
另一半 —— 文件传输、连接诊断、成员页、设置页、错误态家族 —— 一个字都没画。

所以我做的是：**保住 7000 行已调好的逻辑，重写视觉层，并补上设计稿里那些"演出"**。
不是照着 demo 推倒重来（那样会丢掉全部断线重连 / 断点续传 / 滚动手势的调试成果）。

## 2. 设计稿要的、而现有项目没有的数据 —— 逐条判断

> 这是本次最需要「产品判断」的部分。结论：**7 条里只有 2 条值得补，其余建议不做或改造。**

### 2.1 房间分组（全部 / 群组 / 密友）—— 不建议按原样补 ⚠️

**缺什么**：房间数据结构只有 `{ name, alias, pinned, last }`，**没有任何分组/关系字段**。

**为什么不该硬套**：本产品的房间是「知道房名即可进入」的开放模型 ——
没有成员关系、没有好友申请、没有邀请。于是：
- 「**群组**」无法判定：一个房间是不是"群组"？几个人算群？
- 「**密友**」无从判定：没有任何地方记录"谁是我的密友"。

硬做只能两种结果：要么编造（假的），要么给房间加个纯装饰的 `group` 字段（用户点一下手动归类，
功能上等价于"标签"，不如直接用置顶）。

**本项目的决定（已实现）**：换成三个**真实可算**的维度 —— 全部 / 置顶（`pinned`）/ 未读（`unread`）。
零新增数据，零协议改动，且立刻有用（未读筛选是高频需求）。

**如果你仍想要设计稿那套**：最小改动是**纯客户端**加 `room.group` 字段 + 房间右键菜单里一个
"归入分组"，不动协议、不动服务端。工作量约半天。但不建议现在做 —— 先把"未读/置顶"用一阵，
看真实需求再说。

### 2.2 每个房间的在线人数 / 绿点 —— 不要补 ❌

**缺什么**：presence 心跳**只覆盖当前已加入的房间**。切走之后不再订阅，自然拿不到成员在线状态。

**为什么不该补**：想给列表里 40 个房间都显示在线绿点，就得对 40 个房间轮询 presence ——
等于把中继心跳量乘以房间数。收益（一个装饰性绿点）远不抵成本（中继带宽 + 电量 + 复杂度）。

**本项目的决定（已实现）**：绿点**只给当前真的加入了的房间**（`net._room === room && net.canSend`），
其余房间不画。宁可少一个装饰，也不编一个会误导人的绿点。

### 2.3 语音消息 —— 建议明确砍掉，不要吊着 ❌

**缺什么**：完全没有媒体通道；`tb-voice` 按钮在现有代码里就是 `disabled` + "语音消息尚未支持"。

**判断**：真正的语音条需要：录音 API + 音频编码（浏览器侧要 Opus）+ 波形采样 + 时长 +
播放器 UI + 与 P2P 文件通道的衔接。**这是一个独立项目的量级**，不是"补个按钮"。

**建议**：
- 短期：**把按钮去掉**，而不是留一个永远灰着的图标（灰按钮只会让用户反复点）。这是我唯一
  建议"减法"的地方 —— 但我没有擅自删，因为改动 UI 元素属于产品决策。
- 中长期：如果要，走「**语音 = 一个音频文件卡片 + 内联播放器**」的方案，复用现成的 P2P 文件通道，
  不做独立的语音消息类型。这样增量最小。

### 2.4 卡片消息（订餐单 / bento 信息卡）—— 值得做，但要选对姿势 ✅（分两步）

**缺什么**：消息只有两种形态 —— `text`（文本/内联图）与 `file`（文件证明）。
设计稿里那张"美味蟹堡王特供套餐 #082"的订单卡，现有协议**装不下**。

**建议姿势（重要）**：
**不要为每种卡片新增一种消息类型** —— 那会导致协议版本无限膨胀（订餐卡、投票卡、日程卡…）。

正确做法是**两步**：
1. **协议加一个通用载体**：在现有消息上加一个可选的 `payload` 字段（受限 JSON，有 schema 版本
   与大小上限，签名覆盖）。消息本身仍然是一条普通文本消息（可以带一句摘要）。
2. **前端按 `payload.type` 渲染**：`type: "order"` → 订单卡；未知 type → 降级成"这条消息包含
   一个当前版本不支持的卡片" + 原文。这样**老客户端不会崩**，新卡片类型可以独立迭代。

⚠️ 这一步**必须动 Rust 侧签名载荷 → 要 bump 协议版本 + 清历史**（见项目记忆里的协议约定）。
属于独立排期，我没有把它塞进这次改造。

### 2.5 消息级"加密"徽标 —— 不需要补 ❌

端到端加密是**全局属性**（整个连接都加密），不是逐条消息的属性。
在设计稿里它是顶栏一个图标 —— 这个位置是对的。我已经把它做成**可点开的加密说明**，
把"保护了什么 / 没保护什么"讲清楚（房间凭名进入、常驻节点存文本历史、浏览器版只能走中继所以
中继能看到 IP）。给每条消息挂一个锁图标反而会给用户"这条特别安全"的错觉。

### 2.6 搜索"比奇堡居民" —— 不补 ❌

现有只搜房间。搜"居民"需要一份全局用户目录 —— 那是平台级服务。
而且这与项目既有决定一致：**「不做好友簿」**（`sidebar.js` 里写得很清楚：这个项目只借微信的
交互方式，不打算复刻一整套微信）。搜索框当前只搜房间，是对的。

### 2.7 Nunito Sans（Google Fonts）—— 自托管，别引 CDN ⚠️

设计稿的 demo 是 `<link href="https://fonts.googleapis.com/...">`。
本产品面向中文用户、部署在 Cloudflare 上，引 Google Fonts 的后果是：**国内首屏直接白字超时**。

**已实现**：`font-family: 'Nunito Sans', ui-rounded, -apple-system, 'PingFang SC', …` ——
谁把 Nunito Sans 自托管进来就自动生效，没托管也有一份干净的圆润兜底。
**建议**：确认走系统栈（推荐，零成本），或把 Nunito Sans 的 woff2 放进 `frontend/fonts/` 自托管。

## 4. 改造方案（技术）

### 4.1 分层原则：**不动逻辑，只换皮 + 加演出**

现有前端 7000 行，逻辑经过十几轮实测打磨（断线重连的并发守卫、历史翻页的视口保持、
文件续传的位图落盘、IME 组字不误发…）。整体重写的收益是零、风险是全部。

所以采用**三层改造**：

```
① 令牌层 tokens.css      全量重写（配色/字号/圆角/间距/双主题/动效曲线）
② 布局层 layout.css      尺寸与玻璃分层 + 环境气泡层 + 关键帧
③ 组件层 components.css  全量重写视觉，**类名与 DOM 契约一个不改**
④ 结构增强 index.html    只加不删：气泡层/水印/成员药丸/顶栏操作/页脚/筛选 chips
⑤ 演出层 motion.js       新增（环境气泡、连接信息三处、顶栏操作、药丸）
```

**关键约束**：所有被 JS 和自动化用例依赖的 id / class 全部保留
（`#panel-body` / `.msg` / `.bubble` / `.row` / `.rail` / `.pending__item` / `#emoji-pop` …），
所以逻辑代码**一行没为改版而改**。

### 4.2 改动清单

```

frontend/css/layout.css         重写尺寸   64/300/56 + 玻璃分层 + 6 个关键帧（+194）
```

## 6. 需要你知道的判断与妥协

### 6.1 与设计稿的**有意偏离**（3 处）

| # | 设计稿 | 实现 | 理由 |
|---|---|---|---|
| 1 | Nunito Sans via Google Fonts | `'Nunito Sans'` + 系统圆体栈，不引 CDN | 国内会超时导致首屏白字。自托管即生效 |
| 2 | 时间戳 `#90A4AE` | `--fg-faint: #6f8291` | 设计稿那个色在浅底上只有 **2.3~2.6:1**，连 WCAG 最低档（3.0）都不到 |
| 3 | 珊瑚徽标 `#FF7F87` + 白字 | `#F2646E` + 白字 | 原值对比度 ~2.3:1，10px 字号下糊成一团；同色相压暗 6% 后 ~3.6:1 |

第 2、3 条不是审美问题 —— 是**真的读不清**。设计稿给的是一套"看着对"的稿，
但没做可访问性校验。我已把它做成自动化断言（`redesign.py` 的 D 组），
**改成更好看但读不清的颜色会被测试直接拦下**。

### 6.2 改造中真踩到的坑（都已修 + 已加测试守）

1. **深色下药丸文字糊成一团。** 药丸/进度条底色写的是
   `color-mix(in srgb, var(--bg-panel) 70%, var(--bb-seafoam-2))`，
   而 `--bb-seafoam-2`（`#E8F3F1`）是**固定浅色、不随主题变** ——
   深色下混出一块灰绿，"2 人"和"在线"几乎读不出来。
   修法：新增主题化令牌 `--bg-subtle` / `--accent-text` / `--ok-text`，
   并把对比度做成断言。**这条是肉眼看截图漏掉的，量出来才发现。**

2. **1200×80 的宽幅图片在卡片里被压成一条线。** `.imgcard__ph img` 的
   `max-height: 220px` 会让超宽图缩到 13px 高 —— 这是 `image-layout.mjs`
   本来就接受的行为（`image.height <= 220`），我保持原样，没有"顺手优化"
   （那会让那条用例挂）。

3. **顶栏在 390px 宽下把房间名挤成「bb…」。** 右侧有在线药丸 + 三个操作按钮，
   而房间名没有 `flex: 1 1 auto; min-width: 0`。
   修法：让标题组吃掉剩余宽度，并在 ≤760px 隐藏两个次要操作（提示音/加密说明，
   设置页里都有）。**房间名是这个界面最重要的信息，绝不能被先挤掉。**

### 6.3 **已知偏差**（明确留着，不藏）

- `.filecard__recipient-state`（展开详情里的"✓ 已接收 / — 已拒绝"）在浅色下约 **3.9:1**，
  低于 AA 4.5。
  **为什么留着**：`file-recipients.py` 有一条断言——"被拒绝的接收者要用中性色、而不是失败红"，
  而它的判据是"这一行的颜色 `=== var(--fg-faint)`"。换令牌就等于改掉那条回归的保护对象。
  **与其偷偷改测试，我选择保留原令牌**，并把这个偏差写在这里。
  它位于"展开详情"的次级诊断信息里，可接受。
  （修法：把那条断言改成"和普通接收者同色、且不等于失败红"——语义更强，之后就能换令牌了。留给下一轮。）

- **「取消」按钮在纯信息弹窗里是多余的**（`dialog.info` 仍显示它）。
  这是既有行为，改动共享组件有回归风险，本次没动。

## 10. 三个必须说明的技术决定

### 10.1 设计稿有、项目没有的数据 —— 全部换成真数据

设计稿这两页的"氛围文案"密度很高。逐条替换：

| 设计稿 | 项目实际 | 处理 |
|---|---|---|
| 中继「hk-1 香港海沟中继 / eu-1 亚特兰蒂斯洋脊」 | `relay-config.json` 只给 `region: "HK"/"EU"/"FR"` | 映射成 **中国香港 / 欧洲 / 法国**（不认识的代码原样显示）。**不给中继编好听的名字** |
| 「在线 (3000m 专线)」 | 只有 `connected` 布尔 | 显示真实连接态 |
| 「信标载波 142.85 MHz」「丢失率 0.00%」 | 没有这个指标 | **不显示**（信道状态条整条没做） |
| 「加密套件 CHACHA20-POLY1305」 | 前端拿不到 QUIC 的密码套件 | 只说「端到端加密」这个**确定成立**的事实 |
| 「已送达 3000m 海底」（每条消息的对勾） | 文本消息**没有**送达回执 | 不做（有回执的是文件传输，那套是真实的） |
| 「深海信道状态：已同步 1,024 个水波数据帧」 | 没有这个计数器 | 不做 |
| 顶部「● 在线 · 主中继 hk-1 延迟 130ms · 端到端水下加密」 | 中继 id / 延迟 / 加密都真有 | ✅ **做了**（这一条是真的，所以照做） |
| 设置页「客户端版本 v2.4-krab-release」 | 前端**没有**版本号可用 | 页脚改放真实事实（见 §11.4） |

> 判断标准就一条：**用户会不会拿这个数字去排查问题**。
> 会 —— 就必须是真的；不会 —— 那还不如不显示。

### 10.2 「中继行文字重叠」判据改成两轴相交（`sidebar-pages.py`）

原判据是 `id.right > state.left + 1` 就算叠字。那是在"id 与状态同一行横排"的
前提下才成立的近似。设计稿的中继行是**两行**（名称在上、状态在下），
横轴区间天然重叠、纵轴完全分开 —— 旧判据会把正常布局报成叠字。

改成 `crossX && crossY`（真交集）才算重叠。**这是把断言变得更精确，不是放宽**：
旧版会漏掉"上下两行其实压在一起"的真叠字，新版不会。

### 10.3 两处用例选择器随新结构更新（不是放宽）

| 用例 | 原选择器 | 新选择器 | 为什么必须改 |
|---|---|---|---|
| `multi-peer.py` | `.kv` 里找「房间人数」 | `.stat` 里找 `.stat__label` | 状态页的「房间人数」从 `.kv` 行换成了卡片行。**断言原意不变**：状态页要能区分"房间人数"与"Gossip 邻居"（这两个数在旧版曾长期混为一谈） |
| `relay-enabled.py` | `.relay__id` 文本 == `fr-1` | **没有改** —— 改为把区域名放进独立的 `.relay__region`，让 `.relay__id` 只装 id | 与其改测试，不如让 DOM 更干净：人话给人看，机器标识留在自己的元素里 |

## 11. 需要你拍板的三件事

### 11.1 设置页的「实时预览」——**我没做**，建议也不做

设计稿把右侧对话区变成「房间 111 实时预览效果」，带 `测试消息音效 / 恢复默认 / 已自动保存`。

**为什么不照做**：那意味着切到设置页时**把真实聊天替换成假对话**。
对本项目是明确的退步 —— 用户切到设置页往往正是想一边调主题/密度一边看
**自己真实的对话**长什么样，而不是看一段编的示例。而且现有架构里
「设置页」和「对话区」是两个独立区域，替换需要新增一层"预览模式"状态，
收益（好看）不抵成本（多一个模式、多一处状态、真实聊天被遮住）。

**已做的替代**（同样能满足设计意图）：保留真实对话可见（改主题/密度/壁纸
立刻在真消息上看到效果），并把 `测试提示音` 和 `恢复默认` 做成设置面板顶部的
一行工具（`#panel-body` 顶部）。"已自动保存"改成静态的「更改自动保存」提示 ——
**我们没有未保存状态**（每个开关都是即改即存），所以不该显示一个会一闪而过的
"已保存"来假装有状态机。

### 11.2 「声呐拓扑」标签页 ——**我没做**，需要你决定

设计稿那个视图里，**几乎每个数字都是编的**：
`GEO: 11°21'N 142°12'E · 深度 3,000m`（我们没有地理位置）、
`负载 18%`（中继不报负载）、`0.42 秒/周期`（gossip 周期没暴露给前端）、
`256 Bit 强度`。

**能诚实做出来的版本**是有的，因为我们是 relay-only，拓扑其实是固定的三跳：

```
本机 ──(实测 rtt)── 主中继 hk-1 ──(实测 rtt)── 备选 eu-1 / fr-1
```

—— 全部用真实 id / region / rtt / 连接态。**要不要做，你定**：

- **做**：多一个视图标签页 + 一张链路图（约半天）。好处是"为什么慢"一眼可见。
- **不做**：这些信息在状态页的「中继节点网络」卡里已经全有了，只是没画成图。

我倾向**不做**（信息重复，且状态页已经能回答同样的问题），但这是你的产品判断。

### 11.3 「深海消息震动/弹窗」——**我没做**，需要你决定（涉及隐私）

设计稿的第三个通知开关 = 桌面通知 + 震动。

**为什么没做**：这不是换皮，是新产品行为，而且带隐私决策 ——
**系统通知要不要显示消息内容？** 会显示的话，消息正文会出现在锁屏/通知中心上，
与本项目「请勿发送敏感信息」「中继看不到内容」的既有立场有张力；
不显示的话，通知的价值只剩"有人说话了"。

另外它需要申请浏览器通知权限（首次点开开关会弹系统授权框），
这是用户可见的行为变化，不该我替你决定默认值。

**如果你要做**，我的建议方案：默认**关**；打开时才申请权限；
通知里只显示「房间名 · 新消息」（**不带正文**），点击聚焦到该房间。
（约 1 小时）—— 要的话说一声。

### 11.4 设置页页脚的「客户端版本」——我换成了真实事实

设计稿写 `v2.4-krab-release`。**我们前端没有版本号可用**：
协议版本是 Rust 那边的常量（`client-wasm/src/sigfmt.rs` 的 `PROTO_V4 = "v4"`），
**没有暴露到 wasm**；`relay-config.json` 的 `version: 1` 是配置 schema 版本，
写上去会误导。

所以页脚现在写的是不会过期的事实：`端到端加密 · 浏览器版永久 relay-only` + `iroh · QUIC`。

**如果你想要版本号**，最小改动是给 wasm 加一个 `proto_version()` getter
（Rust 改一行 + 重建 wasm 约几分钟 + 产物变大一点点），然后页脚就能显示
`协议 v4`。要的话说一声 —— 硬编码 "v4" 到前端我不建议做，
协议一 bump 页面就开始骗人。

## 15. 拓扑视图：名字换了，内容全是真的

设计稿叫「声呐拓扑」，上面写着 `GEO: 11°21'N 142°12'E · 深度 3,000m`、

照抄的话，这一页会变成"整个产品里看起来最专业、其实全是编的"页面，
而它恰恰是用户网络出问题时最先打开的那一页。

所以：**位置保留、视觉沿用、内容全换成真量、名字改成「中继拓扑」**。

能诚实画出来的拓扑是固定的三跳（浏览器版永久 relay-only，打不了洞）：

```
本机（浏览器）—— 实测 rtt —— 主中继 —— 备选中继
```

三张指标卡也全是真量：

| 卡 | 数字 | 副标题 |
|---|---|---|
| 中继集群 | 配置台数 | 在用 N 台 · 主链路 id（进度条 = 在用占比） |
| 主链路延迟 | 实测 rtt（无探测时显示 `—`） | `id 区域 · 实测 rtt` |
| Gossip 邻居 | 直连邻居数 | 「覆盖网局部视图，**不等于**房间人数」 |

**实现上的一个要点**：拓扑面板是**覆盖层**（`position:absolute; inset:var(--head-h) 0 0 0; z-index:25`），
**不是**把时间线/输入区 `display:none`。因为那两个元素的可见性由
`timeline.open()/close()` 直接写内联 `style.display` —— 两边都改就会互相打架
（表现是切房间后拓扑页自己消失或闪现）。盖住它，零冲突。
`z-index` 必须 > 20（`.composer` 是 20），否则输入区会浮在拓扑上面。

## 17. ★ 发现一个**与本次改造无关**的环境问题：批量传输吞吐不足

### 现象

`file-recipients` 停在 2 MiB「断点续传」那一步。失败瞬间的快照：

```
发送方视图：recipient「用户9230」state=sending, done=128/128, bytes=2,097,152   ← 全发完了
接收方页面：retry.bin        state=active,  done=104/128                        ← 只收到 104
                        （上一次跑停在 68/128 —— 每次停的位置都不一样）
```

`wait_recipient(..., 'done')` 的 45 秒超时到了，接收方还在爬。

**只在大批量步骤失败**：512 KB（32 块）的步骤全部通过；2 MiB（128 块）与 8 MiB（512 块）失败。
按 45 秒收 104 块算，链路上只有 **约 2~3 块/秒**。

### 证据链：为什么确信不是我这次改的

| 假设 | 怎么排除的 | 结果 |
|---|---|---|
| 前端改动引入 | `git stash push -- frontend` 把前端**整体回退到提交版本**，跑同一个用例 | ❌ **原始前端同样失败**，而且更严重（8 MiB 那步卡在 193/512） |
| roomd 状态累积 | `docker compose restart roomd` | 仍失败 |
| 测试浏览器老化 | 重启跑了 **1 天 9 小时**的 Chrome + 清空 profile | 仍失败 |
| 中继容器状态 | 重启 `iroh-relay` 容器（**已连续运行 6 天**） | 仍失败 |
| 主机过载 | `uptime` | 负载 0.50，正常 |
| **我新加的 CSS 动画吃 CPU** | `--force-prefers-reduced-motion` 关掉全部动画（环境是 `--disable-gpu` 软件合成，动画确实可能抢 CPU） | 仍失败 —— 排除 |
| 其它前端改动 | 其余 13 个用例全绿，其中 `multi-peer`(19) / `file-history`(17) 也传文件，只是量小 | 只有大批量失败 |

### 旁证

roomd 自己的中继探测：

```
iroh1.editor.vip (hk-1)  8.69 ms      ← 在用，很快
iroh2.editor.vip (eu-1)  1.014 s      ← 秒级
iroh3.editor.vip (fr-1)  736 ms       ← 秒级
× 3 次 QADv4: probe timed out
```

三台里有两台的往返是秒级。hk-1 的 HTTP 探测虽然快（53 ms），但传输走的是 **UDP 7842 的 QUIC 数据面**，
和 HTTP 探测不是一条路 —— 探测快不代表数据面快。

### 建议（按顺序）

1. **先量，别猜**：项目里已经有 `scripts/transfer-bench.py`，跑一遍拿到真实吞吐曲线。
2. 查 eu-1 / fr-1 那两台中继主机（现在秒级延迟）；确认 hk-1 的 **UDP 7842** 没有被限速/丢包。
3. ⚠️ **不建议直接把用例的 45 秒超时调大。** 那会把"吞吐劣化"这个真实信号盖掉，
   而吞吐劣化会直接影响真实用户传大文件。要用例重新变绿，应该先让吞吐回到正常水平。

> 顺带说明：我在排查过程中**重启了 roomd 容器与 iroh-relay 容器**（项目尚未上线，影响可忽略）。
> 两个容器都正常起来了，relay 的 HTTP 探测 200。

### §17 结论更新（2026-10-05 晚）

**这个问题已经解决，而且我当时的根因判断是错的。**

原开发者接手后定位到：**浏览器的文件数据是经 WSS/TCP 15443 承载的，不是直连 UDP 7842**
（浏览器本来也开不了裸 UDP）。所以服务器当时的 TCP CUBIC 拥塞算法直接决定吞吐 ——
实测那条出口上有重传/乱序、拥塞窗口降到 1~2，持续吞吐只有 **36~38 KiB/s**。

修复：**端口级 BBR**（IPv4 策略路由，只匹配源端口 15443 的中继响应，全局仍保持 CUBIC，
不重启中继/roomd、不动协议与 wasm）。见 [`relay-tcp-bbr.md`](relay-tcp-bbr.md)。

| | 2 MiB 传输耗时 |
|---|---|
| CUBIC（修复前） | 53.5 ~ 57.0 秒 |
| 路由级 BBR（试验） | 3.03 秒 |
| 端口级 BBR（上线后） | **2.44 秒**（512 KiB 1.83s / 8 MiB 7.29s） |

**修复后全量回归：14 个用例 / 236 项断言全绿。**

⚠️ 我在 §17 里写的「传输走 UDP 7842 的 QUIC」是**错的**。
其中"HTTP 探测快 ≠ 数据面快"这个**结论**是对的（所以界面上现在把延迟标注成
「HTTP 探测 ...ms」，避免被误当成实际链路延迟），但**对协议的推理是错的**。
教训：拿不到确证的链路细节不要写成结论。

> 另一条同样值得记的：开发者验证后指出，**与整套文件回归并发跑时 2 MiB 要 28.62 秒
> （71.6 KiB/s），性能断言会正确地失败** —— 也就是说修复只保证"独占链路时能达到"，
> 不保证任意并发与网络条件下都能达到。这条边界他写进了 `relay-tcp-bbr.md`，我没有改。
