# ⛔ 已过时 —— 这个问题已经解决了（2026-10-05 晚）

> **先看这里再读下面。**
>
> **① 问题已修复。** 原开发者定位到根因并在服务器上做了端口级 TCP BBR 策略，
> 现在全量回归 **14 个用例 / 236 项断言全绿**（`file-recipients` 从卡死变成 26/26）。
> 修复说明见 [`../relay-tcp-bbr.md`](../relay-tcp-bbr.md)。**下面的排查建议不用再执行了。**
>
> **② 我下面写的"传输走 UDP 7842 的 QUIC"是错的。** 实际是
> **浏览器文件数据经 WSS/TCP **15443** 承载**，不是浏览器直连 UDP 7842。
> 所以服务器 TCP 拥塞算法（当时是 CUBIC）才会直接决定吞吐 ——
> 这也是为什么 BBR 一上就把 2 MiB 从 53~57 秒压到 2.4 秒。
>
> 我当时的判断只对了一半：**"HTTP 探测快 ≠ 数据面快" 这个结论是对的**
> （所以现在界面上的延迟都改标成「HTTP 探测」了），但**对协议的推理是错的**。
> 教训：拿不到确证的链路细节，不要写成结论，要写成"待确认"。

## 二、现在的问题（唯一一个，需要找人看）

### 2.1 现象

`file-recipients` 用例卡死。它传的最大文件是 **2 MiB**，卡在"断点续传"那一步。

失败瞬间抓到的两份快照（同一个文件，两边视角不一致）：

```
发送方看到：  state = sending,  done = 128 / 128,  bytes = 2,097,152   ← 数据全发完了
接收方看到：  state = active,   done = 104 / 128                        ← 只收到 104 块
```

超时时间到了（45 秒），接收方还在慢慢爬。

**关键特征：每次跑停住的块数都不一样** —— 实测见过 **68 / 104 / 193**。
数字每次不同 ⇒ 不是状态机算错，是**根本没在时限内传完**。

按 45 秒收 104 块算，链路上大约只有 **2~3 块/秒**。

### 2.2 复现

```bash
# 前置：本地静态服务 + 带 CDP 的 Chrome（见 scripts/e2e/README.md 顶部）
cd /Users/patrick/WorkBuddy/iroh聊天室
bash scripts/e2e/run.sh file-recipients
# 日志：/tmp/e2e-logs/file-recipients.log
```

**只有大批量失败**：512 KB（32 块）的步骤全部通过；2 MiB（128 块）与 8 MiB（512 块）失败。
其余 13 个用例全绿，其中 `multi-peer`(19) / `file-history`(17) 也会传文件，只是量小。

### 2.3 已经排除掉的（**别重复做**，每条都实测过）

| 怀疑对象 | 怎么排的 | 结果 |
|---|---|---|
| 前端改造引入 | `git stash push -- frontend` 把前端整体回退到提交版本，跑同一个用例 | ❌ **原始前端同样失败**，而且更严重（8 MiB 那步卡在 193/512） |
| roomd 状态累积 | `docker compose restart roomd` | 仍失败 |
| 测试浏览器老化 | 重启跑了 **1 天 9 小时**的 Chrome + 清空 profile | 仍失败 |
| 中继容器状态 | `docker restart iroh-relay`（该容器已连续运行 **6 天**） | 仍失败 |
| 主机过载 | `uptime` | 负载 **0.50**，正常 |
| 前端新加的 CSS 动画吃 CPU（环境是 `--disable-gpu` 软件合成） | Chrome 加 `--force-prefers-reduced-motion` 关掉全部动画 | 仍失败 —— **排除** |

> ★ 排查这类问题**先做第一步**（git stash 回退前端）：几分钟就能判断是自己的改动还是环境，
> 省掉后面全部试错。

### 2.4 目前的怀疑方向 + 建议怎么查

**旁证**（roomd 自己的中继探测，`docker compose logs roomd`）：

```
iroh1.editor.vip (hk-1)   8.69 ms     ← 在用，很快
iroh2.editor.vip (eu-1)   1.014 s     ← 秒级
iroh3.editor.vip (fr-1)   736 ms      ← 秒级
另外出现 3 次  QADv4: probe timed out
```

三台里有两台的往返是**秒级**。

⚠️ **注意一个容易搞错的地方：HTTP 探测快 ≠ 数据面快。**
- `https://iroh1.editor.vip:15443` 的 HTTP 探测只有 53 ms；
- 但文件传输走的是 **UDP 7842 的 QUIC**，是完全不同的一条路。

所以即使 hk-1 的 HTTP 探测很快，数据面仍可能被限速/丢包。

**建议按顺序查：**

1. **先量，别猜。** 项目里已经有现成的：`scripts/transfer-bench.py`，跑一遍拿到真实吞吐曲线。
2. 查 **eu-1 / fr-1** 那两台中继主机（现在秒级延迟）：它们是不是挂了、带宽被占满、或者网络绕路。
3. 查 hk-1 的 **UDP 7842** 有没有被限速 / 丢包（中继和 roomd 都在 `<OLD_SERVER_IP>` 这台机器上，
   relay 是 Docker 容器 `iroh-relay`，不是 systemd 服务，也不由 `docker compose` 管理）。
4. 浏览器侧两条核对：`chrome://webrtc-internals` 看不到 QUIC，但可以对比"本地两人同房"
   与"跨机"的传输速率，判断是本地环回问题还是链路问题。

### 2.5 ⚠️ 不要做的事

**不要把用例里那个 45 秒超时调大。**
那只会把"吞吐劣化"这个真实信号盖掉，让套件变绿，而**真实用户传大文件一样会卡**。
要用例重新变绿，应该先让吞吐回到正常水平。
