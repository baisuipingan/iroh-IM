# 项目审查 — 2026-10-03

## 范围与结论

审查当前目录的 Rust 客户端、浏览器 Worker、网络状态机、文件传输与历史持久化，并检查部署产物的模块引用和脚本语法。目录没有 Git 元数据，本次是现有源码审查，不是提交或 PR 的差异审查。

**建议先修复 P1 项，再扩大部署或用于敏感文件传输。** 已确认的主要风险是签名载荷可被篡改、文件流缺少发送方授权、续传可能静默写坏文件、房间历史恢复错位，以及异步操作导致实际房间与界面房间不一致。

本次没有修改业务源码、锁文件或部署配置；复现程序在 `/tmp/`，没有攻击线上中继或读取线上用户数据。

## P1 — 优先修复

### 1. 签名字段使用未转义分隔符，可改变已签名消息的语义

- 位置：`client-wasm/src/room.rs:123`。
- 根因：`ChatMessage::canonical()` 把自由文本字段直接用 `|` 拼接，没有长度前缀或转义，序列化不是一一对应的。
- 复现：昵称 `Alice`、正文 `A|B`，改成昵称 `Alice|A`、正文 `B`，规范化字符串完全相同。用当前 Rust 源码生成并验证签名，修改后的消息仍通过 `verify()`。
- 影响：中间转发者或房间内恶意节点可以重新广播语义已变化、但仍带原作者有效签名的消息。
- 建议：对固定字段元组使用无歧义编码，例如确定性序列化或长度前缀；绑定协议版本和房间标识。检查其他 `canonical()` 方法的同类问题，不能只过滤正常 UI 的输入。

### 2. 消息 ID 不参与签名，也没有在验签时重新校验

- 位置：`client-wasm/src/room.rs:146`、`client-wasm/src/room.rs:591`、`frontend/js/ui/timeline.js:178`。
- 根因：验签只核对 `canonical()`，但消息 `id` 不在规范化载荷中；历史和前端又直接信任这个外部 ID 去重。
- 复现：复制一条有效签名消息，只改 `id`，`verify()` 仍为真；把两个版本交给当前 `HistoryStore`，计数为 2。
- 影响：攻击者不持有原作者私钥，也能把同一条消息重放为多条，冒充作者重复发言；不断变更 ID 还可绕过去重、污染历史。
- 建议：从无歧义的完整签名载荷派生 ID，并在接收端重新计算核对，或把 ID 一并签名；明确房间级防重放策略。

### 3. 入站文件流只凭公开的 file_id 路由，没有绑定真实发送方

- 位置：`client-wasm/src/filetransfer.rs:393`、`client-wasm/src/filetransfer.rs:464`、`client-wasm/src/filetransfer.rs:499`。
- 根因：接收登记表只记录 `file_id → channel`。收到数据流时不检查连接的 `remote_id()`，不核对邀请的发送者或文件元信息，也不限制块序号及块长度。
- 复现：使用当前 Rust 源码和真实本地 QUIC 连接，另一个独立身份只提供已登记的 `file_id`，其数据成功进入接收通道；序号 `900000` 也原样交给上层。
- 影响：获知文件 ID 的第三方可以冒充文件发送方，向用户已选择的保存目标注入字节或非预期偏移。文件 ID 在房间邀约中广播，不应被当作授权凭证。
- 关联：`FileCtrl::Invite` 的签名载荷没有包含 `FileMeta.sender`（`client-wasm/src/filetransfer.rs:129`）；修改元信息中的发送者后，控制消息仍通过验签。
- 建议：登记期待的发送者 EndpointId、根哈希、大小、块大小及接收轮次；入站连接和 header 必须匹配，块序号及长度必须合法。邀请中的发送者应等于实际签名者。

### 4. 断点位图未绑定保存文件，换保存位置会跳过不存在的数据

- 位置：`frontend/js/iroh-worker.js:563`、`frontend/js/iroh-worker.js:583`。
- 根因：位图只按 `root_hash:size` 存储。判断 `existingSize < meta.size` 时直接继承位图，新建的空文件也满足这个条件；没有确认选择的是上次那个部分文件。
- 复现：旧位图称已有第 0 块，重新选择空目标文件，当前 Worker 仍向发送方声明第 0 块已存在，只写第 1 块。8 字节目标最终为 `[0,0,0,0,5,6,7,8]`，Worker 发出完成事件。此复现运行真实 Worker 函数，文件 I/O 和 wasm 接收回调使用隔离桩。
- 影响：刷新后换位置、删除部分文件后继续，或另一接收任务使用同一哈希时，可产生缺失内容却显示成功的文件。
- 建议：保存并验证同一个文件句柄，或比对已有块内容；至少不能把空目标认作可续传文件。位图应隔离身份、目标及块大小，且只记录已可靠提交的字节。

### 5. 浏览器接收完成只检查位图，不验证实际大小和整文件哈希

- 位置：`client-wasm/src/wasm_api.rs:507`、`frontend/js/iroh-worker.js:637`。
- 根因：`JsChunkSink::finish()` 只检查各块的位是否已置 1；`root_hash` 最后仅被忽略。Worker 随后关闭文件、删除位图并发出完成事件，没有计算接收文件的 BLAKE3。
- 影响：同样块序号但内容错误、长度错误，或上面第 4 项造成的空洞，均可能被视为完整文件。原生 `BytesSink` 的哈希测试通过，并不代表浏览器 sink 执行了同样校验。
- 验证：静态核对当前 Rust sink 与 Worker 完成路径；换空目标续传复现也确认 Worker 完成路径不检查最终字节。
- 建议：逐块验证长度与范围，在最终成功回执、删除恢复信息之前，流式检查落盘文件大小和整文件根哈希。不得把“QUIC 可靠”或“位图齐了”当作内容校验。

### 6. 房间名到历史文件名的转换不可逆，重启后历史丢失或混入别的房间

- 位置：`client-wasm/src/room.rs:606`、`client-wasm/src/room.rs:667`、`client-wasm/src/room.rs:689`。
- 根因：落盘把非 ASCII 字符替换成 `_`，加载时又把全部 `_` 替换成 `-`；JSONL 中没有原始房间名可恢复。
- 复现：通过当前 `HistoryStore` 实际写盘再加载：`team_a` 的历史变成 `team-a`；`研发群` 和 `产品群` 都写入 `___.jsonl`，随后两间房的历史一起加载到 `---`。
- 影响：服务重启后用户在原房间查不到历史，其他房间可能获得混合历史。这是持久化及房间隔离问题，不只是名称展示问题。
- 建议：以房间名完整哈希或 topic ID 作为文件名，在文件内保存原始房间标识并核对；已有历史需要迁移方案，不能继续尝试反向猜测字符。

### 7. 文件哈希期间切房间，文件会被邀请到新房间

- 位置：`frontend/js/iroh-worker.js:297`、`frontend/js/iroh-worker.js:319`、`client-wasm/src/room.rs:1687`。
- 根因：`pickAndSend()` 接受并保存 `room`，但异步算完哈希后调用 `node.invite_file()`，实际广播使用节点此时的当前房间。期间用户可以继续切房间，没有房间代次校验。
- 复现：开始为 A 准备 `private-A.bin`，在读文件 Promise 完成前切到 B；实际 Worker 调用在 B 发出邀约，但 `outFiles` 仍把它标记属于 A。运行真实 Worker 函数，节点及读取使用可控制桩。
- 影响：原本发给 A 的文件可向 B 披露元信息，并在 B 的成员接受后提供文件内容。
- 建议：发送操作绑定不可变房间标识和加入代次；哈希结束及每次广播前核对，房间已改变则取消或显式提示。文件能力清单也应按房间过滤。

### 8. 重连后旧房间回归与用户待进的新房间并发，界面和底层状态错位

- 位置：`frontend/js/net.js:202`、`frontend/js/net.js:207`、`frontend/main.js:164`。
- 根因：`_goOnline()` 在重新加入旧房间前就同步发布在线事件。主线程监听器立即开始加入用户离线时选择的新房间；随后 `_goOnline()` 又启动旧房间 join，两者没有共用单飞锁。`REJOINED` 还读取操作结束时可变的 `_room`。
- 复现：对实际 `net.js` 使用可控制 Worker RPC，离线时 A→B，先完成 B 再完成旧 A：底层实际房间 A，`net._room` B，通知 `REJOINED(B)`。
- 影响：界面显示 B、发送也被标成 B，实际消息却可能广播到 A；成员、历史及文件能力状态也可能错配。
- 建议：由单一房间控制器串行处理所有 join/leave，包括自动重连；恢复时优先最后的用户选择，用代次淘汰旧结果；事件携带此次操作的不可变房间值。

## P2 — 后续修复

### 9. 切出再切回房间，已有文件卡片无法重建

- 位置：`frontend/js/ui/filetransfer.js:599`、`frontend/js/ui/filetransfer.js:637`、`frontend/js/ui/filetransfer.js:725`；时间线在 `frontend/js/ui/timeline.js:69` 清空。
- 根因：传输 Map 跨房间切换保留，但 DOM 被清空；历史证明、持久化邀约和重复 Invite 都因已有传输记录而直接返回，不再发出卡片渲染事件。
- 复现：真实传输 UI 模块收到邀约时发出 1 次卡片事件，模拟重新载入证明/恢复邀约后发出 0 次。
- 影响：未完成或已完成的文件卡片消失，用户不能在原房间继续处理。
- 建议：区分状态去重和视图渲染；进入房间时根据现存传输状态重建卡片，不必重新发起传输。

### 10. 只用毫秒时间戳翻页，会漏掉同一毫秒内的消息

- 位置：`client-wasm/src/room.rs:638`、`frontend/js/ui/timeline.js:674`。
- 根因：游标是 `before = oldestTs`，服务端筛选严格 `ts < before`，没有 ID 次级游标。
- 复现：当前 Rust 历史存储写入 51 条同一时间戳的不同消息，首页返回 50 条；下一页为空，剩余 1 条永远无法取得。
- 建议：排序和游标使用 `(timestamp, message_id)` 或服务端稳定序号，两端一起调整，避免仅把 `<` 改成 `<=` 产生分页死循环。

### 11. Cargo.toml 与 Cargo.lock 未同步，锁定构建不能通过

- 位置：`client-wasm/Cargo.toml:54`、`client-wasm/Cargo.lock:1597`。
- 根因：manifest 直接依赖 `noq-proto`，锁文件的 `iroh-web` 依赖清单没有它；新增的默认 feature 还引入锁文件没有的依赖。
- 验证：默认 Cargo 镜像先返回 403；通过命令行临时切到可用的缓存镜像后，`cargo test --locked` 明确报锁文件需要更新。
- 建议：在受控环境重新生成和核对锁文件，构建脚本使用 `--locked`。不要用取消锁定构建来掩盖依赖漂移。
