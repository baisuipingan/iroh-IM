# 前端改造与传输吞吐独立复核

## 结论

现有证据不能把传输故障归咎于 UI 重设计。传输内核、Worker 和网络层与 HEAD 没有差异；低吞吐可以用独立 Chrome 进程复现。当前主要瓶颈指向浏览器到香港中继的 TCP/WebSocket 数据路径，尚不能确定是哪家网络、哪段路由或中间设备造成，也没有事发前的同连接指标，因此不能确定退化发生的时间与原因。

## 测量

诊断脚本位于 `output/playwright/handoff-review/throughput.mjs`，使用独立浏览器上下文、唯一房间。中继筛选和 Worker 写入计时只通过测试上下文的请求拦截实施，没有改生产配置或传输代码。

| 场景 | 结果 |
|---|---|
| 默认配置，512 KiB，OPFS | 13.191 秒，逐字节验证成功 |
| 默认配置，2 MiB，OPFS | 56.968 秒，约 36 KiB/s，逐字节验证成功 |
| 仅香港，2 MiB，无写盘 sink | 55.139 秒，约 37 KiB/s；没有真实文件落盘，不能算文件交付测试 |
| 仅香港，2 MiB，OPFS | 53.521 秒，约 38 KiB/s，逐字节验证成功 |
| 默认配置，8 MiB，OPFS | 约 120 秒观察结束仍未完成，最后样本 204/512 块；结束后测试浏览器关闭，不据此断言协议本身失败 |

OPFS 每块写入耗时中位数约 0.8ms、95 分位约 2.4ms、最大约 19.6ms。Worker 25ms 定时器中位数约 24.7ms、95 分位约 33.2ms、最大约 36.2ms。它们解释不了每块数百毫秒的吞吐瓶颈。

`file-recipients.py` 在不受其他关闭标签脚本干扰的复跑中，确实在第 217 行的 2 MiB 完成等待超时；接收端仍 active、74/128 块。它不是文件校验失败证据，也尚未进入第一接收者的续传完成断言。

## 路径与服务器证据

- 浏览器 iroh-relay 的 wasm 实现使用 WebSocket（`wss://...:15443/relay`），不是浏览器直接通过 UDP 7842 上传文件；7842 的 QAD 探测不是本次浏览器数据流。
- roomd 负责房间发现、快照、历史与控制广播，不是文件块的存储或回源服务器。
- 服务端负载约 0.09，relay CPU 约 1.66%，没有高负载迹象。
- TCP 快照中，面向本机出口的一个中继连接：`bytes_sent=5481133`、`bytes_retrans=832196`、`cwnd=1`、`ssthresh=2`，有明显重传和乱序指标。该快照不代表每个连接或整个观测期间，但说明底层路径存在真实异常。
- relay 日志中出现本次接收者 EndpointId 对应的 `Failed to send packet: deadline has elapsed`，以及 TLS/连接建立超时。
- Rust 中已经采用 BBR3 和 2MiB 初始 QUIC 窗口；服务器外层 TCP 仍为 CUBIC。两者不是同一层；只改 Rust 的 QUIC 拥塞算法不能修复外层 TCP 的重传/队头阻塞。

## 前端审查

整体重设计方向合理；把不存在的群组/密友改成可计算筛选、拒绝伪造链路数据是正确决定。独立浏览器的 redesign 回归重新验证得到 108/108 通过，避免共享 CDP 标签页互相关闭干扰；最初共享环境的 5 项对比度失败未能独立复现，不列为产品缺陷。

发现可修复问题：

1. 顶栏提示音按钮只更新偏好和自身图标，没有同步设置页开关。实测偏好已经 false，设置开关仍为 `aria-checked=true`。建议通过偏好事件局部更新两个入口。
2. 拓扑的 Gossip 邻居数依赖 `sidebar.neighbors`，但没有订阅 `PEER_UP/PEER_DOWN`，邻居变化时只能等其他事件才刷新。
3. 拓扑无已连接中继时会回退到第一台 enabled 中继，仍把它称为“主链路”并显示 HTTP 探测延迟。候选配置不等于实际路径，建议明确显示“尚未连接”，并把 HTTP 健康探测与文件数据链路延迟区分。

## 测试工具问题与建议

- `transfer-bench.py` 会关闭共享浏览器标签页、清缓存，不能与其他回归并跑。本次初始共享 CDP 的并行结果受干扰，已排除该轮文件回归结果；后续改用独立进程和上下文。
- 旧 bench 的假句柄路径当前出现 0/128、接收失败，但仍返回退出码 0。它在传输结束后才创建 LogTap，也捕捉不到此前日志，不能用退出码或“无匹配日志”证明链路正常。
- 功能测试应使用总时限 + 无进度时限，继续验证交付与续传；性能测试另设吞吐基线。不要用增大固定超时作为吞吐修复。
- 下一步建议从另一条真实出口跑同样的香港中继测试，并同步采集 TCP 指标；再评估服务器 TCP BBR 的受控实验。香港之外的中继可以在独立上下文中对照，不改全站名单；锚点需要香港中继，不能随手从默认名单移除它。

此次未修改生产代码、部署、重启服务或改服务器网络参数；仅增加本报告及忽略目录内诊断产物。
