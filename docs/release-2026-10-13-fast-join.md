# 2026-10-13 进房提速：修掉「等 10 秒进房 + 孤立提示 + 十几秒看不见人」

## 一句话

「进房要等 10 秒」= 名册把你**自己的旧 id** 报回来 → 客户端去连自己（iroh 直接拒绝）
→ 进房的 8 秒等待预算被白烧满 → 孤立进房；「看不见人」= 常驻节点订阅后的**首条
presence 恰好在还没邻居时播掉**（丢），下一轮要等 15 秒心跳。两处都修了，
线上实测：**进房 ~1 秒、看见人 ~进房即刻**（含页面加载约 3 秒）。

## 根因与证据

### 根因 A：客户端去连「自己」（造成 10 秒 + 孤立）

- 客户端进房先问入口（rendezvous）"这屋里有谁"，入口把它记的成员 id 报回来。
  **同一身份重进房**时，名册里还有你**上一次会话**的 id（35s TTL 内一直在）。
- 客户端把这份 id 列表当 bootstrap 去 `subscribe_and_join` —— 其中"自己"那一条，
  iroh 直接拒绝（`Connecting to ourself is not supported`，agent 日志里就有这条真实告警）。
  全体候选都连不上 → 白等满 `join_timeout`（默认 8s）→ 降级「孤立进房」+ 提示。
- 实测复现（修复前，同身份 6 秒内重进）：`joined@8.4s` + 时间线出现
  「暂时联系不上房间里的其他人」。

### 根因 B：常驻节点的首条 presence 丢失（造成十几秒看不见人）

- roomd 订阅房间后到"和客户端连上"只要 **0.2 秒**（roomd 日志：`已订阅 → 邻居上线`），
  但它那条**订阅瞬间**广播的 presence（以及 15 秒心跳间隔）碰上了空窗：
  首发时刻还没有邻居 → 丢；客户端下一轮要等 **15 秒**心跳才"看见人"。
- 客户端↔roomd 走 DNS/pkarr 发现的最坏路径也是秒级（国内实测 5~9s），
  而"客户端进房后 0.5s 就会拉首页历史"这条路（带中继提示、稳定快）**当时并不带 roomd 自己**。

## 改了什么（核心 5 处 + 2 个单测）

| # | 位置 | 改动 |
|---|---|---|
| 1 | roomd `rendezvous` | **响应里剔除请求者自己的 id**（老客户端不刷新也受益） |
| 2 | roomd `rendezvous` | **把自己也列进名册**（`.with_self_id`）——重进房时客户端有得可拨，不必等 DNS 慢发现 |
| 3 | roomd 消费循环 | **邻居上线（NeighborUp）时立刻补播一次自己的心跳**——不等 15s 心跳 |
| 4 | roomd 历史服务 | **快照里包含常驻节点自己**（`.with_self`，last_seen 取响应时刻、epoch=0）：进房 0.5s 的首页历史就能"看见人" |
| 5 | 客户端 | 进房候选里**剔除自己**（`drop_self`，兜底）；`rendezvous_members_for` 同规则抽出纯函数 |

> 顺带修正一条旧测试：`rendezvous_and_history_are_independent_capabilities` 原来断言
> "入口把**请求者自己**报回来" —— 那正是本次修掉的危险行为。改成**换个客户端来问**：
> 成员要报出、请求者自己不能出现在名册里。

## 线上实测（真实链路，修复前 → 修复后）

| 场景 | 修复前 | 修复后 |
|---|---|---|
| 全新房（roomd 现订阅） | 看见人 **15.35s** | **5.12s**（= 进房那一刻；含页面加载） |
| 同身份快速重进 | 进房 **8s+** 且**孤立提示**；看见人 9.24s | **进房 3.07s / 看见人 3.33s**，无孤立提示（含页面加载；接上 ≈0.3s） |

配置未动：本地/线上仍是同一组中继与常驻节点（香港，HTTP 探测 53~57ms）。

## 反漂移自检（方案 §8 逐条）

1. **房间只是场地**：是 —— 只是把"名册/快照里该不该有谁"报准（剔除请求者、列上常驻节点）。
2. **@ 只按 id 寻址**：是 —— 不涉及。
3. **加 agent = 加 spawn 配置**：是 —— 不涉及。
4. **可单独回滚**：是 —— roomd 与前端各自独立可退。
5. **决策与现实冲突**：无。如实记录：没有证据表明这是最近某次改动引入的回归 ——
   两条机制（名册含你自己旧 id、常驻节点首播丢失）一直存在，重进房/新房间时必然显形。
