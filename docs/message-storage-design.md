# 消息存储方案：调研与设计

> 起因：产品交互上参照微信，于是对"历史消息存在哪"产生顾虑 ——
> 担心"新进房同步全部历史"不符合微信语义，也担心服务端留存隐私。
>
> 本文先**核实事实**（本项目现状 + 微信真实机制 + 开源同行做法），再给设计方案。
> 所有事实性结论都标注了出处；查不到的明确写"没查到"，不做推测。

---

## 一、先说三个必须纠正的前提

在讨论"该不该照微信改"之前，有三件事得先摆清楚。前两条与直觉相反。

### 1. ⚠️ 本项目**没有加密**，只有签名 —— 所以"把历史放服务端"本身不额外泄露什么

`ChatMessage` 的字段是 `id / from / nickname / text / ts / sig / file` —— **`text` 是明文**，
全仓没有任何对称加密层（`grep -i encrypt|decrypt|cipher|aead` 为空）。

| | 现在（有 roomd） | 若去掉服务端历史 |
|---|---|---|
| 消息内容在中继上 | 明文 | 明文（**一样**） |
| 消息内容在 roomd 上 | 明文（落 `data/history/*.jsonl`） | 不落盘 |
| 谁能读 | 房间内的人；加上有 roomd 主机权限的人 | 房间内的人 |

**结论**：服务器留存确实**多了一个副本**（这是真实的差别，主机被入侵/被查时会暴露更多），
但它**不是"加密 vs 不加密"的差别**。中继本来就看得见全部明文。
如果目标是"服务端拿不到内容"，要加的是**端到端加密**，那是另一个课题，
不是"把历史搬到客户端"能解决的。

> 顺带：topic 是 `blake3("iroh-chatroom/v1" + 房间名)`，**房间名可枚举**，
> 所以严格说不是"知道房间名才能进"，而是"猜得到房间名就能进"。
> 这条与存储方案无关，但会影响你对"隐私"的整体判断，一并记在这里。

### 2. ⚠️ 微信群聊"退出期间收不到消息"是**误传** —— 微信有离线消息队列

这是本次调研最值得记的一条。腾讯客服口径（多处一致）：

- **未接收的消息，服务器自动保留 3 天**，3 天后清理，清理后**无法再接收**。
  （注意是"**未接收**"≠"已接收未读"）
- 已接收并下载的内容保存在**设备本地**，只要不删就一直在。
- **"退出登录不会删除任何聊天记录"**，下次登录仍可浏览。

也就是说微信的模型是：

```
服务器：不存历史（用户主动查不到）  +  存"未送达"的消息，保留 3 天（推送用）
客户端：存全部历史（SQLite），换设备就丢（除非迁移/备份）
```

群聊与私聊在这一点上**行为一致**：退出期间的消息，服务器帮你留着，
**3 天内登录就能补到**，超过 3 天就永久丢失。不是"只能收到登录之后的消息"。

### 3. 微信群聊：**新成员看不到加入之前的任何历史**

这一条是明确的（多来源一致，与官方"记录只在设备本地"的机制自洽）：
老成员的记录在他自己手机上，新成员加入时没有任何来源能补给他。

想要历史只能靠人肉：**群成员可以主动"转发/分享聊天记录"给新成员，上限 99 条**。

### 微信 vs 本项目 · 逐项对照

| 维度 | 微信 | 本项目现状 |
|---|---|---|
| 服务端存历史 | ❌ 不存（官方：服务器不保存任何聊天记录） | ✅ roomd 落盘 `data/history/*.jsonl` |
| 端侧存历史 | ✅ SQLite，永久 | ❌ **完全不存消息**（IndexedDB 只存文件位图） |
| 换设备 | 丢历史（除非迁移/备份） | **不丢**（roomd 还在） |
| 退出/离线期间的消息 | 服务器留 **3 天**，登录可补 | **不丢**（roomd 存着，随时拉） |
| 新成员看加入前历史 | ❌ 看不到（只能人工转发，≤99 条） | ✅ **能看到全部** |
| 消息加密 | 传输加密；E2EE 需开"聊天记录迁移"/企业版 | ❌ **明文**，只有签名（防伪造，不防偷看） |
| 服务端删消息 | 不适用（本来就不存） | 单房间上限 5000 条 / 16 MiB，磁盘 64 MiB |
| 历史可见范围 | 仅参与者、仅本机 | **任何知道房间名的人都能拉到**（历史 ALPN 无鉴权） |

**一句话总结差异**：微信是「**客户端权威 + 服务端只做 3 天送达缓冲**」，
本项目是「**服务端权威 + 客户端零存储**」—— 两者正好相反。

## 二、开源同行怎么做（4 个流派）

调研了 6 个有代表性的项目，事实如下（出处见文末）：

| 项目 | 客户端存哪 | 服务端存历史 | 新成员看历史 |
|---|---|---|---|
| **Mattermost** | Redux persist → localStorage（消息主体不持久） | Postgres，持久 + 保留策略 | 公开频道**默认可见全部** |
| **Rocket.Chat** | Zustand + React Query（IndexedDB 仅缓存） | MongoDB 全量 + 按天自动删除 | 公开频道**可见全部** |
| **Zulip** | 未查到 | Postgres，持久，**连编辑历史都存** | 公开全可见；私有分 `shared`/`protected` |
| **Matrix / Element** | **IndexedDB**（`useIndexedDB` 默认 true） | 持久存（E2EE 存密文） | **可配置四档**：`joined`(默认,只看加入后) / `invited` / `shared` / `world_readable` |
| **OpenIM** | 客户端本地 db（缓存） | **MySQL 全量** + MongoDB 离线消息 **14 天** | 未查到明确策略 |
| **Signal** | 本地 SQLCipher SQLite（桌面端） | ❌ **不存消息内容** | 未查到 |

### 两个流派

**流派一 · 服务端权威历史**（Mattermost / Rocket.Chat / Zulip / OpenIM / Matrix 数据层）
服务端是唯一真相源，端侧只是缓存或干脆不存。协作/客服类产品**默认让新成员看到历史**。

**流派二 · 纯端侧存储**（Signal；IRC 风格的 Matrix 房间）
服务端只转发放，历史全在端上。换设备就丢，新成员看不到历史。
**"不补历史"在这里是设计选择，不是缺陷。**

成熟产品通常是**混合**：Matrix = 服务端权威 + IndexedDB 缓存 + **可配置可见性**；
OpenIM = MySQL 全量 + **14 天离线队列** + 客户端缓存。

> 仿微信的开源项目参考价值有限：搜到的多是**只做 UI 的克隆**（Flutter/React 界面）
> 或 MERN 教学 demo（直接 MongoDB 存消息、无保留策略、无可见性控制）。
> 唯一架构相关的 `tangjienan/wechat_clone` 只有 7 个 commit，不宜当权威。

### 从开源方案里可直接借用的两个机制

1. **Matrix 的 `history_visibility` 四档** —— 目前最成熟的"可配置历史可见性"范式，
   语义可以照搬（默认 `joined` = 只看加入之后）。
2. **OpenIM 的「全量历史 + 短保留离线队列」双轨** ——
   把"长期历史"与"送达保证"拆成两件事分别设保留期，比一个笼统的 TTL 清晰。

## 三、设计：这是个**决策**，不是"照着微信改"

先说结论：**我建议保留服务端历史，不要照搬微信的"端侧权威"。** 理由见下。

### 为什么不建议照搬微信

微信那套是**被约束逼出来的**，不是最优设计：

1. **它的约束我们不存在**。微信要服务 13 亿用户、每天海量消息，
   全量存服务端在成本上不可行。我们是自建小规模（roomd 单机 + 64 MiB/房间上限）。
2. **它的代价用户已经习惯了**：换手机丢历史、新成员看不到历史、
   3 天不登录就永久丢消息 —— 这些是**缺陷，不是特性**，只是用户被驯化了。
3. **照搬过来我们的体验会倒退**：现在是"换设备/刷新/新成员都能看到历史"，
   改成端侧权威之后，刷新页面就等于**历史清零**（浏览器端没有持久 SQLite
   那种强保证，IndexedDB 会被浏览器在存储压力下清理）。
   用户会觉得"越改越烂"，而理由是"为了像微信"—— 不成立。
4. **要模仿的是交互，不是实现**。微信的交互习惯（气泡、会话列表、待发送区）
   我们已经抄了，这部分是对的；但**存储实现是后端架构决策**，
   该看约束与目标，不该看对标的 UI。

### 如果仍然想要"更像微信"的语义，有三个档位可选

按改动量从小到大：

**档位 A · 只改"新成员可见性"**（改动最小，语义最贴近微信）

给房间加一个 `history_visibility` 概念（照搬 Matrix 的语义）：

| 取值 | 含义 |
|---|---|
| `all`（现状） | 新进房的人能看到全部历史 |
| `since-join`（微信语义） | 只能看到**自己加入之后**的消息 |
| `none` | 进来就是空的，纯实时 |

实现要点：
- 服务端要记录"**每个 peer 首次进入该房间的时间**"（roomd 已经有快照表，加一个 `firstSeenMs` 即可）
- 拉历史时按 `max(requested_before, my_first_seen)` 截断
- ⚠️ **签名/协议不用动** —— 这是**服务端过滤**，不是协议变更。这也是它比"端侧存储"划算的根本原因。
- ⚠️ 安全边界要写清楚：这是**服务端**的过滤，防的是"普通用户看到不该看的"，
  防不住"有能力直连 roomd 的人"（见第一节第 3 条：历史 ALPN 本就无鉴权）。
  要真防，得先解决 ALPN 鉴权。

**档位 B · 加端侧缓存（不作为权威）**

用 IndexedDB 缓存最近 N 条消息，作用：
- 刷新/重连**先出内容**（不用等 roomd 响应），体感更快
- roomd 挂掉时仍能看到最近的历史

⚠️ **必须让 roomd 保持权威**，IndexedDB 只做加速。理由：
Matrix 的 IndexedDB 也是缓存（官方文档明确说它让"不必完整 sync 一次"）；
一旦让端侧当权威，就掉进"换设备丢历史"的坑，且与现状相比是**退步**。
技术选型：**IndexedDB**，不要用 localStorage（只有 ~5 MB、同步阻塞主线程、
只存字符串）。正好项目里已有 `iroh-transfers` 库的用法可复用。

**档位 C · 加端到端加密（真正解决"服务端看得到"）**

这才对应"隐私顾虑"的根因。但它是**另一个课题**（密钥分发、新成员如何拿到历史密钥、
多设备同步），工作量远大于 A/B，且会与"新成员看历史"产生直接冲突 ——
Element 专门为此做了"E2EE 历史密钥分享"才解决：
admin 设 `Members (full history)` 后，新成员通过 to-device 加密消息私下收到历史密钥。

**建议顺序：现在什么都不做（保持档位 0），等你确认产品定位后再选。**
如果一定要动，**档位 A 的性价比最高** —— 改动局限在 roomd 的过滤逻辑，
不动协议、不动客户端、可随时回退（改回 `all` 即可）。

### 一个必须同时修的问题（与存储方案独立，但更紧急）

第一节对照表里那行「历史可见范围：**任何知道房间名的人都能拉到**」——
历史 ALPN **没有应用层鉴权**，房间名就是全部凭据，而房间名可枚举。
这意味着**现在任何人猜到一个房间名，就能读走该房间的全部历史**。

这比"历史存服务端还是客户端"严重得多。如果要提升隐私，
**优先修这个**，而不是搬存储位置。可行方向：
- 房间名加一个共享密钥（`房间名` + `密钥` 共同派生 topic，密钥只在参与者间传递）
- 或给历史 ALPN 加基于房间成员的鉴权

## 四、结论速览

| 问题 | 结论 |
|---|---|
| 微信聊天记录存哪？ | **客户端 SQLite**，服务器**不保存**（腾讯客服官方口径） |
| 那未上线期间的消息看不到？ | **不是**。服务器会存"未送达"的消息 **3 天**，3 天内登录可补；超期永久丢失 |
| 微信群聊新成员能看到历史吗？ | **看不到**，只能靠群成员人工转发（上限 99 条） |
| 本项目现在怎么存？ | 服务端权威（roomd 落盘），**客户端零消息存储** |
| 要不要照微信改成端侧权威？ | **不建议**。那是被规模成本约束逼出来的方案，我们的约束不同，照搬是体验退步 |
| 那想更像微信怎么办？ | **档位 A**：给房间加 `history_visibility`，服务端过滤"只看加入后"。不动协议、可回退 |
| 隐私顾虑的正解？ | ①修历史 ALPN 鉴权（紧急）②加 E2EE（大工程）—— **都不是"搬存储位置"** |
