# 2026-10-15 进房补投：桥重启窗口里错过的 @ 不再丢（room-bridge 0.2.5）

## 背景（用户现象）

> "为什么@了等了半天没反应" —— room `agenthub` 里 @OPENCODE，没有任何回复。

排查（roomd 侧证据）：

1. **那条 @ 根本没到服务器**：在 roomd 的历史库里搜 `信源` / `xlsx` / 文本片段，
   **0 命中**；agenthub 最后一条历史停在上午 09:18。用户气泡是自己端的
   **乐观渲染**（`net.send()` 返回即画），消息实际没离开浏览器 ——
   用户的标签页在跑 16:20 修复之前的旧页面（发送半死掉、永不重拨；见同日
   `release-2026-10-15-nickname-join-and-dead-peer.md`），**刷新即可**。
2. 同一分钟还叠了第二个坑：用户 **20:01:33** 重启了 room-bridge
   （roomd 日志：`邻居下线 8ad72780… 20:01:04Z` → `邻居上线 … 20:01:37Z`），
   而那条 @ 也标着 20:01 —— **就算浏览器是好的**，发在桥重启窗口里的 @
   一样会丢：适配器是**在消息之后**才进房的，gossip 不补历史。

第 2 条是这一次要修的东西（第 1 条前端修复昨日已发，只需强刷）。

标签页状态的时间线（roomd 日志，端点 `26ff3891…` = 用户身份）：

- `01:17–03:12Z`（09:17–11:12 CST）：以真名 `用户7454` 心跳；
- `07:00–10:33Z`（15:00–18:33 CST）：以**空昵称**心跳（旧页面的空昵称
  rejoin bug 实锤；UI 靠 localStorage 显示名字，看不出异常）；
- `10:23–10:33Z`：邻居反复上下线；`10:33:58Z` 起**彻底静默** ——
  发送方向连接死亡（死邻居 never-redial），但接收方向仍活（截图里
  `2 人`/`在线` 是真的，OPENCODE 的心跳还在进来）→ 于是"界面一切正常、
  发出去的消息原地蒸发"。

## 修复：进房补投（`agent-pi/src/room/backfill.ts`）

每次看到 `joined` 事件做一次补投：

1. 拉最近一页历史（默认 50 条）；
2. 挑出「**不是自己发的** + **没见过** + `ts` 在窗口内（默认 3 分钟）」的；
3. 用 `client.emit('event', …)` 按**与实时消息完全相同的事件形状**重放 ——
   触发判断 / 去重 / 冷却 / 预算全部走同一条管线，补投路径**没有任何特判**。

两个关键设计：

- **去重持久化**（`<IROH_AGENT_HOME>/room-seen.json`，每房最近 200 个 id，3s 防抖落盘）：
  没有它，进程重启一次就会把窗口内的 @ 再回一遍；用消息 id 而不是时间戳，
  不受各端时钟偏差影响。
- **只在窗口内补投**：不翻旧账（重启后不会去回早上/昨天的问题）。
