# 威胁模型：房间级「可选加密」（V6.3 评估）

> 方案 §V6.3 要求「先写威胁模型」再定范围。本文给的就是这个模型与一份**建议**。
> 结论先行：**建议暂不做**；若所有者要推进，本文末尾列出最小可行路线与改造面。

## 1. 现状：每一环看得见什么

| 环节 | 现在看得见 | 说明 |
|---|---|---|
| 传输链路 / 中继（relay） | **只看得见密文** + 元数据（谁连谁、流量大小/时序） | QUIC/TLS + iroh；内容不进 relay |
| 常驻节点 roomd（服务器） | **明文**：文本历史、快照、名片档案 | 它是房间里的一等成员——这正是"翻记录就能认识人"的实现基础 |
| 房间名 | 它就是**访问凭据** | 知道房名即可进房：新人能读**全部历史**、能发言 |
| 同房间成员 | 互相可见（聊天语义如此） | 端到端在本产品里=“对成员透明” |
| 服务器磁盘 / 备份包 | 明文（含 roomd 的 SQLite） | 备份是运维必需品（`roomd-backup.service`） |

## 2. 威胁清单（对谁设防）

- **T1 链路窃听 / 中继运营者**：现状**已防**（内容加密；relay 只看元数据）。
- **T2 服务器 / roomd 托管方**：现状**不防**（明文历史）。自托管时"托管方就是所有者本人"，
  价值有限；若将来把 roomd 托管给第三方，这条才开始有分量。
- **T3 知道房名的陌生人**：现状**不防** —— 陌生人进房即可读全部历史、冒充搭话。
  **这是最真实的驱动**（房间名会转发、会张贴、会被猜）。
- **T4 成员设备被查 / 成员恶意转发**：任何客户端加密都防不住持有明文的成员，本文不展开。

## 3. 「房间级可选加密」会破坏什么（关键取舍）

把房间内容改成"只有持钥成员能解"（E2E），与当前架构的多个**卖点**正面冲突：

1. **常驻节点的文本历史、搜索、快照（名片/文件清单）全部失效**——除非把 roomd 放进
   信任圈（那就不再防 T2）。
2. **所有 agent / 召唤器**必须持钥才能工作（它们靠读内容触发/回复）——分发与管理成本随着
   "房间里越来越多 agent"线性上升。
3. **新成员的密钥分发**：若密钥仍能从"房名"推出，陌生人一样解得开（等于没加密）；
   真正的分发必须**带外**（邀请制/二维码），这与"知道房名就能进、进来就翻历史"的
   产品模型冲突 —— 相当于引入第二种房间（"私密房间"）。
4. 与 V6.1/V6.2 刚建立的**结构化、可聚合**的成员状态（mentions/名片）配合变复杂：
   签名与加密两层叠、密钥轮换、成员移除后的前向保密（要么引入 MLS 级协议，要么接受弱保证）。

## 4. 建议（留给所有者拍板）

**暂不做**房间级可选加密。理由：

- 它要防的 T3，用**更便宜的手段**能缓解大半：房名用高熵串（现在的 `房间名=凭据` 已经是
  这个模型）、敏感内容别放常驻历史、需要私密的沟通走一次性房间；
- 它要防的 T2，自托管场景下不成立（所有者即运营者）；
- 代价却是把项目最有特点的三样东西（常驻记忆、agent 生态、翻记录识人）同时打折。

## 5. 若要做：最小可行路线与改造面（先记下来，别现拍脑袋）

1. **定义"私密房间"**：房名仍是入口，但内容用**带外分发**的房间密钥加密（邀请链接携带）；
2. **协议**：对 `Wire` 各载荷做一层 AEAD 封装（签名在内、加密在外或反之，需定死）；
   密钥轮换/成员移除策略先按"不做前向保密、轮换=新房间"的最朴素版本；
3. **常驻节点降级**：私密房间里 roomd 只存密文（历史/名片/快照对持钥者本地重建）；
   召唤器要单独配 key（或私密房间不支持召唤）；
4. **测试**：跨端 golden（加密前/后各一份）、密钥轮换 e2e、旧端表现（明确拒绝而不是乱码）；
5. **迁移**：与 v6 一样是破坏性换代，需要独立公告与一次切。

以上第 2-5 步是**一整个大版本**的量级——这也是把它归为"可选、由所有者拍板"的原因。
